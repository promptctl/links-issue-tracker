Bulk-create or update issues from a file. The file's extension picks the
format: .yaml or .yml is the YAML bulk format, which creates or updates;
any other extension is the JSON tree spec, which only creates.

Both formats reject any key they do not name, so a misspelled field fails
the whole file rather than being dropped. Every rule the file alone can
answer is checked before anything is written — required keys, duplicate
ids, and every rule below, about values and about references within the
file — and a file that breaks one exits 3 with nothing changed. A JSON
file can name only its own records, so one that passes this check is
written whole.

A YAML file can also name issues that already exist, and a rule about
one of those is checked as the file is written: an id, parent or
blocked_by naming no existing issue, a parent that is not an epic, a
blocked_by naming an epic the new issue sits under or another non-epic
issue directly under its epic, or an update that changes type to or
from epic. Every create and update is written before
any blocked_by, so a file that breaks one of these fails partway
through. See Results for what rollback covers.

JSON tree spec (creates only)

  An array of records, one per issue:

    [
      {"local_id": "epic-x", "title": "Build the exporter",
       "type": "epic", "topic": "exporter"},
      {"local_id": "design", "parent": "epic-x", "title": "Design it",
       "type": "task", "topic": "exporter", "priority": 1},
      {"local_id": "epic-y", "blocked_by": ["epic-x"],
       "title": "Ship the importer", "type": "epic", "topic": "importer"}
    ]

  Keys: local_id, title, type, topic, priority, description, prompt,
  plan, assignee, labels, parent, blocked_by. Anything after the closing
  bracket is an error.

  local_id is required on every record: it is how parent and blocked_by
  name another record before real IDs exist. Those two may only name a
  local_id in this same file — a real, already-existing issue ID is
  rejected here; use the YAML format to hang new issues off issues that
  already exist.

  title, type, and topic are required on every record. priority may be
  omitted and then defaults to 0.

YAML bulk file (creates and updates)

  One issue per YAML document, documents separated by ---. The file is a
  stream of documents, not a list: a top-level YAML sequence is rejected.

    local_id: epic-x
    title: Build the exporter
    type: epic
    topic: exporter
    ---
    title: Design it
    type: task
    topic: exporter
    parent: epic-x
    ---
    id: lit-exporter-7fq2
    title: Build it, renamed
    labels: [reviewed]
    reason: retitled after review
    ---
    id: lit-exporter-9kd1
    rank: top

  id decides what a document does, and nothing else does. Absent, the
  document creates. Present, it updates exactly that issue; an id
  matching no existing issue is an error, never a create. One id may not
  appear on two documents.

  A create document requires title, type and topic exactly as a JSON
  record does, and takes the same optional keys plus lane. local_id is
  optional here (a create without one is reported under its new real ID).
  parent and blocked_by may name either a local_id in this file or the
  real ID of an issue that already exists. reason is rejected on a
  create: there is no prior value for it to annotate.

  An update document must set at least one of title, description, prompt,
  plan, type, priority, assignee, labels, lane, rank. A document carrying only
  id, or only id and reason, has nothing to apply and is rejected; reason is
  free text recorded on the change event, not itself a change. --by
  names the actor those change events record; only a YAML file with an
  update document takes it, and any other import given --by is refused.

  Four keys are rejected outright on an update document, each belonging
  to something else: topic (immutable — no command changes it after
  create), local_id (create-only), parent (reparent with lit parent set),
  blocked_by (wire dependencies with lit dep add).

  rank: top, on a create or an update document, orders the file's issues.
  Every document that says it is stacked at the top of its issue's frame
  in file order: the first leads, the next ranks directly below it, and
  so on, exactly as lit rank set <ids in file order> would, and one such
  document alone is lit rank <id> --top. top is the only value. The order
  is written after every create and update, in one step, so it lands
  whole or not at all, and a file whose order has already landed changes
  no rank when it is imported again. An issue ordered against issues
  outside its epic is ordered by its epic instead, as lit rank set orders
  it, so a file that ranks two issues of one epic together with an issue
  outside that epic is refused.

Values both formats enforce

  title may not be empty or only whitespace, on a create or an update.

  type is one of task, feature, bug, chore, epic.

  priority is 0 (normal) or 1 (urgent). No other number is accepted.

  topic is lowercased with runs of non-alphanumerics collapsed to a
  single dash, and must be 3 to 30 characters after that, so a topic of
  "x" fails.

  labels are lowercased and deduplicated, and may not contain commas.

  assignee may not contain a comma.

  id, local_id, parent and blocked_by values are matched literally:
  leading or trailing whitespace in any of them is rejected, not trimmed.

  A local_id may not be used twice in one file, a record may not name its
  own local_id in its own blocked_by or name any entry there twice,
  parent/blocked_by references within the file may not form a cycle,
  and a record may not be blocked_by an epic it sits under in the file,
  nor a non-epic record by another non-epic record of the same epic:
  rank orders the work inside one epic.

  A file with zero records or zero documents is an error.

Results

  Created issues land at the bottom of the ranked order. Output is the
  number created and one "name -> real id" line each, where the name is
  the local_id (or the new real ID when the document gave none), followed
  for a YAML file by the number updated and their IDs, and, when the file
  ranks, the order written, as lit rank set reports it.

  On any failure, issues created earlier in the same run are rolled back
  on a best-effort basis by deleting them; updates already applied are
  not rolled back, since there is no prior state to restore. If the error
  reports that rollback leaked IDs, run lit doctor.

  A full-database export is a different shape than either format above;
  load one with lit backup restore.
