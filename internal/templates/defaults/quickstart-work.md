Finding and starting work (lit)

If the user asks you to pull a specific ticket: `lit ls --limit [limit] --search [query]`
If the user asks you to pull without specifying a ticket: `lit next` (the single top workable leaf, ready to start)
If the user asks for the backlog, the ranking rationale, or wants to read the pull order they are re-ranking: `lit backlog` (workable items in rank order, blocked items inline so the queue shape is legible; a focus label narrows it, and `--all` lifts that for one run)

Get details for a ticket: `lit show <id>` — for a ticket in an epic it auto-prints the epic plan (siblings in rank order, their status, your "you are here" spot, and any cross-epic dependencies).

Selection is claims-first, not rank-only: `lit next` serves this checkout's own claims before anything else — a ready lane you already hold, then any lane of the same epic no other checkout holds fresh, stale claims included — and only falls through to the global top-ranked lane once your checkout holds nothing.

A lane belongs to the checkout, not to your session. Every session running in one checkout is the same claimant, which is what lets a fresh session pick up where the last one stopped with no re-briefing — and it means two sessions working one checkout at the same time share one lane and will be routed to each other's tickets. When a ticket in flight is assigned to someone other than you, `lit next` names them instead of telling you to carry on. Usually that is the session that worked this checkout before yours and the ticket is yours to continue — check that nothing is still running against it, then continue. lit cannot tell a session that stopped from one still working, which is why it names them rather than deciding for you. A ticket with no assignee names nobody, so silence there is not proof the work is yours. Changing `--assignee` does not move a lane: the receiving checkout takes it with `lit start --take`, and until it does, the lane stays where it was.

Start work: `lit start <id>` — claims the ticket under your session identity and moves it to in_progress. Starting global work (no live claim yet) claims that lane for this checkout, so a fresh session here routes back to it automatically. If `lit next`/`lit backlog` show the lane claimed by another checkout and still fresh, `lit start` refuses and names the holder; pass `--take` to confirm the takeover deliberately (an interactive terminal is prompted instead). A stale claim's takeover proceeds on its own but prints who held it and how far they got — check for unmerged branches or PRs on that lane before building on it. Work claimed elsewhere stays visible in `lit next`/`lit backlog` (who has it, how stale), but only a stale claim makes it a bare `lit next` target — taking it transfers the lane to this checkout; a fresh claim is reached only by `lit start --take`.
