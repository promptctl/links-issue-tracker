Finding and starting work (lit)

If the user asks you to pull a specific ticket: `lit ls --limit [limit] --search [query]`
If the user asks you to pull without specifying a ticket: `lit next` (the single top workable leaf, ready to start)
If the user asks for the backlog, the ranking rationale, or wants to read the pull order they are re-ranking: `lit backlog` (workable items in rank order, blocked items inline so the queue shape is legible; a focus label narrows it, and `--all` lifts that for one run)

Get details for a ticket: `lit show <id>` — for a ticket in an epic it auto-prints the epic plan (siblings in rank order, their status, your "you are here" spot, and any cross-epic dependencies).

Selection is claims-first, not rank-only: `lit next` serves this checkout's own claims before anything else — a ready lane you already hold, then any lane of the same epic no other checkout holds right now, then a ready ticket outside the epic that gates it — and only falls through to the global top-ranked lane once your checkout holds nothing, or once your epic has nothing workable left.

A lane belongs to the checkout, not to your session. Every session running in one checkout is the same holder: `lit next` serves each of them the checkout's lanes, and each runs `lit start`, `lit phase` and `lit done` on their tickets without ceremony, which is what lets a fresh session pick up where the last one stopped with no re-briefing. Another checkout — a worktree of this one, or another clone — is a different holder: `lit next` routes it around the lane, and its `lit start`, `lit phase` and `lit done` are refused with a line naming the holding checkout (`<id> is held by <checkout> (active <ago>)`); `--take` on that same command crosses the hold deliberately. So work is done from the checkout that holds it: run `lit next`, `lit start` and every git command for a ticket from inside that checkout (`claimed here: <path>` on a lane's claim line names it), and keep it for the next ticket `lit next` serves it rather than opening a new one per ticket. When a pick belongs in a worktree of its own, `lit start <id>` runs from inside that worktree, since the claim lands on the checkout `lit start` runs in. Changing `--assignee` does not move a lane: the receiving checkout takes it with `lit start --take`, and until it does, the lane stays where it was.

Start work: `lit start <id>` — claims the ticket under your session identity and moves it to in_progress. Starting global work (no live claim yet) claims that lane for this checkout, so any session here routes back to it automatically while the claim is live — six hours without an event of its own anywhere in the lane expires it, and an expired claim is not a claim: `lit next` routes by rank, the lane is offered like any other, and nothing about the expired claim is shown. If `lit next`/`lit backlog` show the lane claimed by another checkout, that claim is live: `lit start` refuses and names the holder, and `--take` confirms the takeover deliberately (an interactive terminal is prompted instead). A ticket left in_progress in a lane nobody holds is abandoned work — `lit next` offers it, and `lit start` picks it up with no ceremony; check that lane for unmerged branches or PRs before building on it.

Record the phase as the work moves: `lit start` puts the ticket in `plan`, where you write its plan (`lit update <id> --plan-file <path>`; `lit workflows show phase-plan` says how to plan it). Run `lit phase <id> --to impl` when you start writing its code, `lit phase <id> --to review` when its PR opens, and `lit phase <id> --to merge` when review is done and the merge is under way; then `lit done <id>` once it has merged. A statusline and other sessions read the phase to see where the work stands, so it is only as current as the last `lit phase` you ran.
