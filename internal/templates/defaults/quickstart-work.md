Finding and starting work (lit)

If the user asks you to pull a specific ticket: `lit ls --limit [limit] --search [query]`
If the user asks you to pull without specifying a ticket: `lit next` (the single top workable leaf, ready to start)
If the user asks for the backlog, the ranking rationale, or wants to read the pull order they are re-ranking: `lit backlog` (workable items in rank order, blocked items inline so the queue shape is legible; a focus label narrows it, and `--all` lifts that for one run)

Get details for a ticket: `lit show <id>` — for a ticket in an epic it auto-prints the epic plan (siblings in rank order, their status, your "you are here" spot, and any cross-epic dependencies).

Selection is claims-first, not rank-only: `lit next` serves your own claims before anything else — a ready lane you already hold, then any lane of the same epic nobody else holds right now, then a ready ticket outside the epic that gates it — and only falls through to the global top-ranked lane once you hold nothing, or once your epic has nothing workable left. In that second case `lit next` says why the epic stopped and names the ways on: when something a ticket here could clear blocks the epic (not a blocker waiting on an outside event), file the ticket that clears a blocker under the epic with the `lit new --parent <epic> --top` it prints and make that blocker blocked by it with `lit dep add <blocker> --blocked-by <new>`; or start the ticket it served from outside the epic.

A lane is held by one session in one checkout: the session that started its latest ticket, in the checkout it ran from. Only that holder is served the lane's tickets by `lit next`, and only it runs `lit start`, `lit phase` and `lit done` on them without ceremony. Any other session — in the same checkout, in a worktree of it, or in another clone — is refused, and the refusal names the holder (`<id> is held by <session> in <checkout> (active <ago>)`); `--take` on that same command takes the ticket over deliberately. So a fresh session picking up where a stopped one left off takes its lane with `--take`; check that nothing is still running against it first, because lit cannot tell a session that stopped from one still working. Working from a plain shell with no session and no `--by` is an identity of its own: it keeps working its own tickets in its checkout, and only a different identity needs `--take`. Work is done from the checkout that holds it: run `lit next`, `lit start` and every git command for a ticket from inside that checkout (`claimed here: <path>` on a lane's claim line names it). When a pick belongs in a worktree of its own, `lit next`'s start advice says `from a worktree of its own off the trunk (not …)` before `lit start <id>`, and `lit start <id>` runs from inside that worktree, since the claim lands on the checkout `lit start` runs in. A second holder establishing work in one lane is reported by `lit next` and `lit backlog` as `contested by`. Changing `--assignee` does not move a lane: the receiving session takes it with `lit start --take`, and until it does, the lane stays where it was.

Start work: `lit start <id>` — claims the ticket under your session identity and moves it to in_progress. Starting global work (no live claim yet) claims that lane for your session in this checkout, so `lit next` routes you back to it while the claim is live — six hours without an event of its own anywhere in the lane expires it, and an expired claim is not a claim: `lit next` routes by rank, the lane is offered like any other, and nothing about the expired claim is shown. If `lit next`/`lit backlog` show the lane claimed by another checkout or session, that claim is live: `lit start` refuses and names the holder, and `--take` confirms the takeover deliberately (an interactive terminal is prompted instead). A ticket left in_progress in a lane nobody holds is abandoned work — `lit next` offers it, saying so, and `lit start` picks it up with no ceremony; check that lane for unmerged branches or PRs before building on it.

Record the phase as the work moves: `lit start` puts the ticket in `plan`, where you write its plan (`lit update <id> --plan-file <path>`; `lit workflows show phase-plan` says how to write and revise it) and have a reviewer with a fresh context pass it (give them the instruction "Law-review the plan of <id>: run `lit quickstart review` and follow it."). Run `lit phase <id> --to impl` when you start writing its code, `lit phase <id> --to review` when its PR opens, and `lit phase <id> --to merge` when review is done and the merge is under way; then `lit done <id>` once it has merged. A statusline and other sessions read the phase to see where the work stands, so it is only as current as the last `lit phase` you ran.
