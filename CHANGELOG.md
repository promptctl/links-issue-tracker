# Changelog

All notable changes to `links-issue-tracker` (the `lit` CLI) are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- The `/next` skill — the procedure an agent follows to pull the next ticket and start work — now ships from the lit binary itself: `lit init` (and `lit quickstart --refresh`) writes it to `.claude/skills/next/SKILL.md`, marker-delimited and reconciled on re-run like the `AGENTS.md` / `CLAUDE.md` sections, and it resolves project > global > embedded like every managed template, so a repo that wants a different `/next` overrides `next-skill.md` through the same layering as `quickstart-work.md` (the new short alias for `--eject` is `next-skill`) — with one added shape rule: the override must be either plain marker-free text or exactly one `BEGIN/END LIT INTEGRATION` block, and anything else fails init loudly rather than corrupting the managed file. Until now the skill lived in the separate `memento` plugin, versioned apart from the binary whose commands its every instruction names — which is how it kept teaching `lit ready` long after that command was retired, with nothing in either repository able to notice. The skill's YAML frontmatter must sit at byte 0 for the harness to parse it, so the managed markers sit inside the body rather than wrapping the file: the frontmatter is written once at creation and is the user's afterward, and lit owns only the marker-delimited body. The text lands byte-identical to the memento copy — still naming `lit ready` — deliberately: a move that also edits is a move nobody can review, and the corrections are this epic's later children. (links-workflow-rls7.1)
- No shipped template may name a command lit does not dispatch: a gate test now walks every managed template's embedded default, extracts each taught `lit <command>` invocation, and refuses any whose command the registry does not dispatch as a live command — so the next retirement fails the build the moment it leaves stale teaching text behind, instead of rotting silently the way `lit ready` did in the /next skill. Both halves of the check are derived, never hand-maintained: the template list comes from `templates.Names()` and the command set from the `commandSpecs` registry, the same table the cobra dispatch is built from. **The trap the predicate had to dodge is that retired commands still dispatch** — `ready`, `queue`, `assign`, `ls-at`, and `overview` stay registered so a stale invocation gets a documented pointer and exit 3 rather than cobra's unknown-command noise — so any "does this token resolve?" test passes the exact string that caused the incident. Retirement is therefore now a stated property of the registry rather than an inference from runners or exit codes: `CommandSpec` gains a `Retired` field, authored only through a new `retiredSpec` constructor that assembles retirement's three facets (hidden from the advertised surface, marked for the gate, dispatchable only to a pointer at the replacement) — and since a same-package struct literal is beyond what the Go type can refuse, a registry coherence test holds every retired row to all three facets, including that its runner actually answers with the retirement pointer; the five retired rows each shrank to a single constructor call. The mirror-image false positive is also pinned: the gate reads `Retired`, never `Hidden` and never help output, so a hidden-but-live command stays teachable — and since every `Hidden` row in today's registry is also retired, that distinction is exercised by a synthetic-spec test rather than claimed from a registry that currently cannot tell the two fields apart. What counts as an invocation is the template language's own quoting, not a guess over prose — markdown templates are scanned only inside inline code spans (prose like "when lit errors" or "lit tracks tickets" never reaches the matcher), while the shell hook template is scanned whole, since it is code and even its warning strings quote real invocations. Scope stays at top-level command names: flags, argument shapes, and prose accuracy are a different and much larger problem, and naming a dead command is the failure that actually happened; a retired *subcommand* (`bulk import`, whose retirement lives in its family table as a hidden row plus a runner, not yet as stated data) would today pass the gate through its live parent, and closing that gap by making family-level retirement legible is filed as links-workflow-mrb6. Proven by breaking it, not by watching it pass: appending "Take a look at the backlog (`lit ready`)" to the shipped next-skill.md turned the gate red with the offending template and token named, and the same refusal is pinned permanently in-suite by table cases that run the retired, unknown, and prose shapes through the gate's own extraction path. (links-workflow-rls7.3)

### Changed

- The shipped `/next` skill now sends the agent to the quickstart for which command answers which question, instead of keeping its own copy of that reference. The skill had grown a duplicate account of finding work — "Take a look at the backlog (`lit ready`)", plus a paragraph describing the epic-and-top-ticket overview that command used to print — and the drift landed in the copy nobody could test: `lit ready` was retired while the skill kept teaching it. The fix deletes the account rather than swapping in a live command name: the Finding-work section opens by naming the seam (the quickstart topics are the reference; the skill is the procedure) and keeps only what exists nowhere else — the uncommitted-changes triage, the open-PR check, orphans before fresh work (now wired to `lit orphaned`, which the quickstart does not cover), and the working-the-ticket steps, all byte-identical apart from the splices the deletion forced. Fresh-work selection is a bare "run `lit next` and start the ticket it hands you", deliberately free of selection semantics: what selection *means* — epic exhaustion, the blocked-epic diagnostic — is links-workflow-rls7.4's ground, and this rewrite leaves it no stale prose to fight. The epic-and-top-ticket overview itself is deleted, not relocated, and no replacement command is filed: its three procedural uses each have a sharper surviving home (`lit next` for selection, `lit backlog` for queue shape, `lit orphaned` for abandonment), and the epic-shaped view survives where it is actually consumed — `lit show <id>` prints the epic plan once a ticket is held. Every lit invocation the skill now names dispatches in this binary; repos pick the new body up on the next `lit init` or `lit quickstart --refresh`. (links-workflow-rls7.2)

## [0.11.0] - 2026-09-03

### Added

- The docs that say Dolt is lit's storage are now wired to the migration state that will falsify them. Eight registered claims across six user-facing sites — README.md's "Issues live in an embedded Dolt database", "State is a Dolt database, so issue history is real", "issues are rows in an embedded Dolt SQL database", and "`lit sync` mirrors that Dolt data through your existing git remotes", plus four fragments across docs/architecture.md's storage-model and sync-model sections — are all true today. `design-docs/event-store/design.md` §migration plans the five states that end that: at S3 events become truth, sync becomes git refs, and Dolt shadows as rollback, which falsifies every one of them, and S4 deletes the machinery and makes them absurd. **The defect was the missing link, not the prose.** design.md already carries per-section status lines and a per-state Status column, and flipping a status is defined there as part of closing the work that ships it — but neither mechanism reached README.md or docs/, so the failure mode was a released README describing storage the binary no longer has. It surfaced during the store-seam circle-back sweep for claims the 0.9.0 release made stale: nothing was stale, but the sweep was manual, and nothing would have caught it if something had been. The fix is `internal/docsclaims`: a registry of the claims — each entry a (file, verbatim quote, falsifying state) triple — and a gate test in the normal `go test ./...` PR lane that parses the §migration table's Status column at test time. The package keeps no copy of which states are built; campaign state is read from the table itself. **The check runs in both directions.** While the falsifying state's status is `destination`, the claim must still be PRESENT in its doc, so rewording or deleting the prose fails the test and forces a registry update instead of silently retiring the guard; once the status is anything other than `destination`, the claim must be ABSENT, and the failure message names the file, the quoted claim, the state, and its new status, and says to rewrite the prose and drop the registry row. An unrecognized status value counts as built — it trips the gate for a human to look at rather than passing it — and claim matching is whitespace-normalized, so re-wrapping a paragraph never fires the gate. A test rather than a status line in the README, because a status line in user-facing prose is user-hostile, while a failing test reaches exactly the person flipping the state; and since design.md already makes the status flip part of closing the shipping work, the doc-update duty on the future S3 work is now self-enforcing, with no S2/S3/S4 tickets pre-written to carry it. The README itself was deliberately not rewritten — not even to a safer "issues live in a local database" — because the claims are true and "Dolt" carries real reader value, the versioned-history story and the dolthub link; vaguing the prose to avoid future edits trades reader value for editor convenience, where the gate makes the future edit obligatory instead of forgotten. Verified by mutation: flipping S3's status cell to `built (unreleased)` made the gate fail 8 times, once per registered claim, and rewording one README sentence made the presence direction fail with the update-the-registry message. (links-event-store-dlob)

### Fixed

- AGENTS.md's managed `LIT INTEGRATION` block once again matches the current `lit init` template. The file's own preamble promises the block is "exactly what `lit init` writes", but it still carried an older, more forceful edition ("CRITICAL… You MUST run `lit quickstart` immediately… a **hard requirement that cannot be deferred or ignored**") that `internal/templates/defaults/agents-section.md` had since replaced with the current calmer wording — the one CLAUDE.md's copy already matched. The block was refreshed by running `lit init` itself, so the fix is the tool's own regeneration path doing exactly what the preamble claims it does. (links-docs-8mdb.4)
- README.md's 60-second tour no longer claims `lit done` is followed by "a two-step confirm". There is no confirm: every lifecycle transition is single-phase, and `lit done` closes the ticket in the one invocation (the guidance it prints afterward never gates the close). The tour is a new reader's first mental model of finishing work, so its example now matches what the command does. (links-docs-8mdb.3)
- `docs/troubleshooting.md`'s "Integrity errors" section no longer tells the reader to run `lit fsck --repair`, a command that doesn't exist — a dead end hit exactly when it hurts most, mid-incident. The section now gives the real path: `lit doctor` to diagnose, `lit doctor --fix` to repair. (links-docs-8mdb.2)

- Bare `lit upgrade` now resolves its own target — the latest published release — instead of rejecting the invocation with a usage error demanding `--to`. The defect was self-inflicted guidance: lit's own remote-schema-ahead sync-failure remediation prints `lit upgrade` as the fix, an invocation the command refused to run, so an agent following lit's printed advice dead-ended and sent its user hunting for a version tag. The target comes from the same release feed `scripts/install.sh --latest-release` consults (GitHub's `releases/latest`, read through the new `release.LatestResolver` seam), and the feed-served tag passes through the same accept shape as a user-typed `--to` before it touches a manifest URL. Latest is `--to`'s default value, not a second mode: the pipeline runs the same stages either way, and `--to <tag>` still pins. Already being at or ahead of the latest release is a friendly no-op (exit 0, naming the kept version — `releases/latest` names the most recently created release, not the highest version, so a backport tag can be "latest" while the installed binary is newer; the default path never moves backward) — but only for the bare form; an explicit `--to` at the running version still installs, deliberately, as the reinstall path for a damaged binary. When the workspace schema is ahead of even the latest release, the bare invocation is refused loudly with both schema ranges named, never soothed with "already current". The success line now prints from → to. `lit downgrade` keeps requiring `--to`: a backward move stays deliberate. The command also gains its missing `docs/cli-reference.md` section — it was the only version-traversal command without one. (links-upgrade-8ynx)

## [0.10.0] - 2026-08-27

### Added

- A workspace that never runs `lit sync push` now gets its storage collected anyway, and a workspace that pushes constantly now gets the collection it was never actually receiving. Compaction used to ride entirely on the push path, so a repo with no remote — or one that simply goes a long time between explicit pushes — had nothing reclaiming its store at all. Measured on a fresh remote-less workspace: 150 mutations with no push grew `noms` from 132 KB to 6,528 KB, and the per-mutation cost was still *climbing* as it went (≈17 KB/mutation over the first 25, ≈65 KB/mutation from 100 to 150), because every commit rewrites more of the prolly tree and no intermediate version is ever collected. A single shallow pass took that store from 6,060 KB to 1,864 KB — **69% reclaimed in 0.26s**. **But the more surprising half is that the push path was not collecting either.** `SyncCompactAndPush` called `DOLT_GC` with no arguments, which is `types.GCModeDefault`, and in Dolt's `value_store.go` the old generation is rewritten *only* under `GCModeFull` — `oldGenFinalizer.SwapChunksInStore` sits inside `if mode == GCModeFull`, while default mode sets `oldGenHasMany = OldGenGCFilter()` and treats everything already archived as live by fiat. Dolt's own `dolt gc --help` says it plainly: the default "will never collect data from deleted branches which has previously made its way to the old generation". So lit had pinned the shallower of Dolt's two depths by passing no argument, and the deeper one was unreachable from anywhere in the codebase. This repository's own store showed the consequence: 72 MB of `noms` that was ~100% old generation spread across **148 `.darc` archives** — one 44 MB base from the day the store was built, then a drip of 8–26 small archives per active day, tracking push cadence exactly — with an 8 KB new generation. Running the shallow pass on it reclaimed **zero bytes in 0.11s**, a pure no-op, because 8 KB was all the new generation had to give and a shallow pass cannot touch the 72 MB where the waste actually was; the deep pass took it to 61,848 KB and **148 archives down to 2** in 1.36s, with all 645 issues and 3,280 commits intact afterward. The deep pass reclaims everything the shallow one would and then the old generation as well, so the two nest rather than divide — what separates them is cost, not coverage, and the numbers above are each depth meeting the store where it happened to be: the shallow pass found an empty new generation here and a full one on the fresh workspace. That is why the depth is now a value (`storage.GCMode`) the caller supplies rather than a mode hardcoded into one call site: the choice is about what a pass is worth paying for, and a store owed both wants one deep pass rather than two. **Each depth is triggered where its own problem actually occurs.** The shallow pass is owed when the chunk journal reaches 16 MB, and runs from the post-command slot the inline receive already occupies — after the command's own engine has closed, since `DOLT_GC` transitions the store read-only mid-run and collides with a live engine, never with none. Its cost tracks the journal rather than the store, because that depth does not traverse the old generation at all, so a fixed threshold buys a constant sub-second stall at any store size; 16 MB is Dolt's own auto-GC signal at 1/8 its 128 MB threshold, which was sized for long-lived servers holding databases orders of magnitude larger than an issue tracker's. The deep pass is owed when the old generation reaches 64 archives. Both entry points — the backstop and `SyncCompactAndPush` — consult that one policy rather than each carrying their own, so neither can drift on what a depth is for. What accumulates archives is **a shallow pass, not a push**: each one appends an old-generation archive and removes none, whichever entry point ran it — measured on a real store, a single shallow pass moved it from `journal 239.0 KiB -> 0 B, old-generation archives 0 -> 1`. So a workspace crosses the deep threshold at the rate it *collects*, not the rate it pushes: quickly when it pushes often, slowly but still surely when the backstop is the only thing that ever fires. That is also why the deep threshold counts archives rather than estimating waste — the count is really shallow passes since the last deep collection, and both entry points feed it. A workspace that pushed for a while and then stopped is the case that needs both depths, and it gets both. Compaction stays **inside** the commit lock, unlike the remote-cache prune that landed beside it: the prune is safe unlocked because an abandoned mirror is unreachable by construction, an argument that says nothing about a pass that rewrites the store everyone else is reading. **The engine owns the judgment, not the caller.** `CompactIfDue` is a capability method, so no CLI code counts archive files or reads journal bytes — what makes a pass due is a fact about how an engine stores data, and a command layer that re-derived it would need to understand a storage layout the contract exists to hide. That boundary is not a convention here; `TestCLIAndAppReachStorageOnlyThroughTheContract` rejected the first version of this change, which had exactly that leak. Dolt's own `auto_gc` was checked first and is unavailable rather than merely unchosen: `dolt_auto_gc_enabled` defaults to `1` but is inert without an `AutoGCController`, which only Dolt's `sqlserver` and `dolt sql` construct — so that variable reads "enabled" inside lit's embedded engine while nothing collects — and adopting it would mean a background thread, the mechanism class this work is barred from. `lit sync compact [--full]` is the explicit, schedulable form, and it deliberately requires no remote, since a solo workspace is exactly the one with nothing else to collect it. Verified by driving the shipped binary, not only by tests: a real workspace accumulated 66 archives, and one ordinary `lit new` — printing nothing about compaction — took it to 1 archive and `noms` from 1,032 KB to 480 KB with all 67 tickets intact. (links-storage-bd8w.2)

### Fixed

- `lit sync push` now collects the abandoned git remote mirrors nothing else was ever going to, taking this repository's Dolt cache from 142 MB to 97 MB in a single run. Dolt gives every git-backed remote its own complete bare-git-repo mirror at `<db>/.dolt/git-remote-cache/<sha256(remoteURL|ref)>/repo.git`, keyed on that URL with only `git+` stripped from its scheme and any query and fragment cleared (normalized, but nowhere near canonicalized), and **nothing in Dolt ever deletes one** — a grep of all of doltcore for prune, evict, or cleanup comes back empty, and `dbfactory` exports no helper for so much as naming the path. So any re-spelling that survives that stripping, including one that does not change which repository it points at, sends the next open to a fresh key, clones a whole new mirror, and abandons the previous one permanently. Two ordinary events had already done exactly that here — a GitHub org rename (`brandon-fryslie` → `promptctl`) and an scp-style-vs-`ssh://` re-spelling of the *same* repository — leaving 45 MB in three dead mirrors of two long-gone spellings beside the 97 MB live one. `SyncCompactAndPush` now sweeps them on the same run that already compacts with `DOLT_GC`: `DOLT_GC` compacts `noms`, this collects the other half of the store's local footprint. The sweep runs after the push and **outside** the commit lock, and both halves are load-bearing. After the push, because the push has just opened the live mirror, so that directory provably exists and the derivation has something true to check itself against. Outside the lock, because the lock was never what made removal safe — a directory is eligible only when no configured remote derives its key, and every open reaches a cache through a configured remote's key, so an abandoned mirror is unreachable by construction — and holding the cross-process writer-exclusion lock across an unbounded filesystem walk would block every other `lit` mutation on the workspace to buy nothing. **The obvious sweep — derive the expected key for each configured remote, delete every directory that does not match — is the catastrophic one, and it was caught only because it was tried.** "This directory's key is not in the expected set" means two incompatible things: the mirror is genuinely abandoned, or the derivation is wrong and never produced the live key at all. Left collapsed, a broken derivation reads as evidence about the disk — the prune deletes the LIVE mirror, the next push silently re-clones it, and the feature inverts into churning the entire cache on every push while reporting success and raising no error anywhere. That was not hypothetical. This repository's remote is `git+ssh://git@github.com/./promptctl/links-issue-tracker.git`, Dolt's canonical normalization of a home-relative scp-style path, where the `/./` segment is load-bearing; a derivation that drops it yields a perfectly plausible key naming no directory on disk. Candidate spellings were hashed by hand against the real directories on disk, and the live 97 MB mirror was among the ones no naive candidate named. **So `planRemoteCachePrune` carries one rule and one refusal.** The rule: a directory is abandoned when no configured remote derives its key. The refusal: when some configured remote has NO directory on disk and there is something to delete, the two cases can no longer be told apart, so the prune declines wholesale and removes nothing. A store that has never pushed trips neither — it has no directories, so there is nothing to delete. The duplication of Dolt's unexported key function is pinned by a test that performs a real git-backed push, lets Dolt create the cache directory itself, and asserts the derivation names that exact directory, so an upstream scheme change fails a test instead of eating a live mirror; and only lowercase-hex sha256 directory names are eligible at all, so nothing Dolt did not write can be classified abandoned. The prune reports rather than fails, because a push that already succeeded is not the prune's to retract — a cache that failed to collect costs disk, a failed `lit sync push` costs the user their sync — and it surfaces through a new engine-neutral `SyncPushResult.Maintenance`, kept separate from `Message` so the `raw` payload key stays the engine's verbatim push output. The CLI prints that line above the push line in **both** plain and `--verbose` output, because a refusal reachable only behind `--verbose` is still silent where it counts, and prints nothing at all when the prune found nothing, so an ordinary push gains no line. The routine case is the only thing emptiness can mean: work performed, work declined, an I/O failure, and progress cut short by a later failure all render non-empty. Verified end to end here: the live mirror survived, a subsequent `lit sync fetch` succeeded with no missing-chunk errors, and a second push reported "Everything up-to-date" without re-cloning. (links-storage-bd8w.1)

## [0.9.0] - 2026-08-27

### Added

- lit's storage contract has a second implementation, and it shares no code with the first. `internal/storage/memory` implements the whole of `storage.Store` with nothing but Go values — no SQL, no disk, no schema — and passes the same `internal/storage/conformance` suite the Dolt engine passes. Until now that suite was a regression net written from what one engine does; with two unrelated implementations running it, each statement in it is a statement about the contract rather than about Dolt. **The independence is deliberate and it cost something.** Four things the Dolt engine does are pure functions of model values reachable through contract methods alone — the field-patch diff, the status/retention transition planners, the frame resolution behind the rank intents, and the compensating bulk apply — so lifting them into the contract package would have looked like the obvious one-source-of-truth fix. It would also have destroyed the proof: two engines calling one implementation is one implementation wearing two hats, and a green conformance run would then say nothing at all about those paths. The suite is the shared definition of behavior; the code is not. Where the suite under-pinned a behavior, Dolt's current behavior was the tiebreak, since S0's gate is that nothing observable changes. **The second implementation is what freed rank from its encoding.** Dolt stores a fractional index string per issue and computes midpoints, which is why it also offers a `FixRankInversions` repair for orders that have come to contradict themselves; here the total order IS a slice, `Issue.Rank` is rendered from a position at read time and stored nowhere, and every intent is a detach followed by a placement — so a stored rank that disagrees with the order it claims to encode is unrepresentable and there is nothing to repair. That the same suite passes both is the evidence that the intent vocabulary, not fractional indexing, was ever the contract. The engine declines all seven capabilities and says so through the same discovery mechanism the Dolt engine answers with: it has no remote to sync with, no divergence to settle, no history to check point, no faults of its own making to repair, no versioned shape to migrate, and no engine-native language to run a raw statement in, so `storage.Offered` reports the empty set and `storage.Sync.Of` hands back an `UnsupportedError` naming both the capability and the engine. `memory.New` requires a workspace id rather than defaulting one, because attribution is a complete pair or nothing and an engine built without one could only ever record unattributed events — silently. Not wired into any CLI path (that is links-store-seam-q35v.4) and making no performance claim, though the whole suite runs against it in 7ms where Dolt takes ~3s, which is the fixture tax the testperf epic measures. (links-store-seam-q35v.3)

### Changed

- The two engines disagreed about ordering in two places, and both are now settled in the contract instead of waiting to be discovered by the differential oracle. A listing's order ends in the issue id as its last key, always — without it, sorting on any field with duplicate values (two issues sharing a title, a priority, an assignee) left the tied rows wherever the engine happened to hold them, and the two engines held them differently: Dolt broke ties by id, the memory engine by rank. History is now ordered by creation time and then by event id, where Dolt sorted `created_at, id` over random uuids and the memory engine returned true recording order. The memory engine was changed to match Dolt in both cases, which is deliberately the WORSE answer of the two: an engine that is right where the other is arbitrary still reads as divergence, and S1's oracle would spend its signal on a difference already known and catalogued. Ordering that actually carries happens-before arrives with the event store's Lamport positions, for both engines at once. Both rules are stated on `storage.IssueReader` and pinned by conformance cases that fail if either engine drifts — `list_breaks_sort_ties_by_id` and `events_are_totally_ordered`, plus `list_accepts_exactly_the_contract_sort_fields`, which checks each engine's private sort-key binding against the new `storage.SortFields` rather than trusting two hand-maintained copies of one closed set to stay equal. A third case, `list_sorts_status_by_stored_encoding`, pins a fault on purpose: sorting by status reads the stored column, which is NULL for every epic, while filtering by status reads derived state — one listing with two meanings for the word. Correcting it moves observable output, so both engines were made wrong identically and the correction is its own ticket. (links-store-seam-q35v.5)

- Two names in the contract package stopped overclaiming, and one mode went away. `storage.Checkpoint.CommitSHA` is `Anchor`: its documented contract was only ever "an identifier the engine that captured this state can resolve back to it", and the old name obliged an engine that anchors by log offset to invent a hash. It had been deferred alongside `SyncStatusReport.DoltVersion` on the grounds that renaming a field changes rendered output — true of `DoltVersion`, which renders through `lit sync status` as `dolt_version`, and simply not true of this one, which has no consumer outside the engine at all. `storage.Repairer.Fsck(ctx, repair bool)` is now `FixIntegrity(ctx)` with no flag: the `repair=false` arm was a literal duplicate of `Doctor` — the body read `if repair { … }; return s.Doctor(ctx)` — and nothing in the repository ever passed `false`. The Repairer interface now reads as one examine verb and two fix verbs, matching the CLI's `--fix` registry one for one. (links-store-seam-q35v.5)

- `design-docs/event-store/design.md` absorbed what S0 actually built, per the charter's rule that the docs take on a resolved position when the work closes. The §migration table gained a per-state status column and S0 is marked built, since a five-state section could not previously say that one of them had shipped; the S0 row now mentions the second engine, which is the thing that makes the interface a boundary rather than a description of Dolt. New prose names the seven capabilities and the rule that split them, the conformance suite and why it — not the interface — is the specification, and the engine factory, which matters because it is the single place S1's dual-write decorator installs. The two settled ordering rules are recorded there as well, since S1's gate asks for an empty oracle diff and was unmeetable as written against two known divergences. (links-store-seam-q35v.5)

- The flip: nothing above `internal/store` holds a Dolt engine any more. `app.App.Store` is a `storage.Store`, every engine in lit is constructed by the new `internal/engine` factory, and every capability beyond the core contract is reached with `storage.<Cap>.Of` — so the concrete engine type appears in no signature, no struct field, and no test fixture outside the engine's own package. **The factory is one function, not three.** `store.Open`/`OpenForRead`/`OpenSync` became `engine.Open(ctx, mode, path, workspaceID)` with the mode as data, because the campaign's later states each attach here: S1's dual-write decorator wraps what the factory returns, S2 changes which engine is behind it, and S4 deletes a row from its table — and a decorator with three seams to wrap is a decorator with two places to forget. The concrete type is erased at that one point, which is what makes the seam hold without anyone having to remember it. **Capabilities are asked for at real boundaries, never re-asked inland.** `lit sync` resolves `Syncer` once for the whole family, in the adapter that already owned the store's lifecycle, and hands handlers a session carrying it; `lit sync reconcile` asks separately for `Reconciler`, because an engine whose arrivals cannot conflict offers sync and declines reconcile (`design.md` §sync), and the inline receive treats that decline as an ordinary reconcile error — traced and surfaced — rather than inventing a fallback that would record an unsettled divergence as clean. `doctor` asks for `Repair` once and passes the interface to its fix registry, so a fix cannot reach an engine with nothing to repair; `restore` asks for `Sync` and `Import` before it reads, writes, or backs anything up, so an engine offering one and not the other cannot strand a restore half-done; `downgrade`'s pre-existing narrow `schemaDowngrader` is now satisfied by the `SchemaMigrator` the capability hands back. Nothing pairs `OfferedBy` with a type assertion — `Of` is the parser and `OfferedBy` is derived from it, so asking both would be the re-checking `Of` exists to delete. The alias block links-store-seam-q35v.1 and .2 left behind is gone, the engine's own files now spell the vocabulary `storage.X` like every other caller, and `ParseSortSpecs`/`ParseBulkSpecs`/`ParseImportTreeSpecs` moved to `internal/storage` beside the schemas they parse. Nothing user-visible changed; the existing suites are the oracle for that and they are green. (links-store-seam-q35v.4)

- The seam is now unrepresentable to cross rather than merely discouraged. `TestCLIAndAppReachStorageOnlyThroughTheContract` parses the source of `internal/cli`, `internal/app`, and `cmd/lit` — tests included, since a fixture that opens a concrete engine is how a boundary erodes first — and fails the build if any of them names the engine type or a constructor. **It enumerates the rest instead of banning it, and the distinction is the honest part.** The ticket asked for app and CLI to import the engine package nowhere at all. - `cmd/lit`'s mirror-quiescence cleanup now genuinely joins the detached on-change mirror, closing the flake that has been failing master's race lane since that lane landed: `TestPushFailureBannerReachesMutationOnlySession` failed on two of the three master commits after it (`e8c4072` and `031feb1` red, `799a53d` green) with `TempDir RemoveAll cleanup: unlinkat …/.git/links: directory not empty` — the directory was not failing to be removed, it was being REFILLED while `RemoveAll` walked it. The cleanup waited on the single-flight sync-push lock and justified that choice with the claim that a mirror losing the race "exits without opening a store, writing a trace, or creating a file". That last clause was false, and the comment asserting it is what kept the bug hidden: `filelock.Acquire` opens its lock path `O_CREATE`, so a mirror that only loses the race still creates two entries in the very directory being swept — the mirror beacon and the sync-push lock it just tried. Worse, the cleanup *elected* that branch, since holding the push lock through the sweep is precisely what makes a just-spawned mirror lose. `-race` did not cause the failure, it widened it: a slower mirror lands its two creates later, and the failure needs one of them to fall inside `RemoveAll`'s own window — after it has read and emptied the directory, before its `rmdir` — which is why the lane flakes rather than failing every time. There is no branch of the mirror that is safe to race, so the cleanup now waits for the process to be GONE rather than for it to be harmless, on two kernel-visible observations whose ORDER is the correctness: the mirror-pending marker is read FIRST — stamped by the claimant BEFORE the spawn and cleared only by a mirror that has already entered its cycle, it is the only evidence that covers a mirror between `cmd.Start` and its own first instruction, a live process the kernel cannot yet show anyone — and the beacon is probed LAST, where `BeaconUnheld` is kernel proof that no mirror and no claimant was running at that instant. Deciding on the beacon last is the same discipline `ProbeMirrorBeacon` already applies internally; reversed, a mirror could enter and clear the marker between the two reads and the pair would report quiescence over a running process. The push lock is deliberately no longer part of the join at all — taking it cannot silence a late mirror, only elect the one branch that still creates files, and holding it through the sweep starves the marker's only clearer, so the join could never complete. Failing to reach quiescence within the budget is now a loud test failure naming both observations rather than a logged note followed by the confusing `RemoveAll` error it predicts. `internal/cli`'s claim protocol grew the one exported seam this needs, `MirrorOwed` — the same "is a spawn still outstanding" question the protocol asks itself, with an unreadable marker returning an error instead of a false, so a caller gating a destructive step on it never receives "I could not tell" wearing the shape of "nothing is owed" — and `MirrorBeaconVerdict` grew a `String` so a failure says `beacon verdict: answered` instead of sending its reader to count `iota`. Production behavior is unchanged; the audit of sibling `cmd/lit` tests found the three `awaitMirrorQuiescence` call sites to be the complete set, since a mirror spawns only under on-change cadence and every other test driving a real `lit` binary either disables auto-sync outright or pins cadence to `on-push`, so it spawns no mirror at all. (links-testing-tt0c.5)

- `TestRecheckMirrorPending` no longer races the kernel's coarse inode clock. The test failed intermittently in CI — most visibly on PR #404, a two-line `CHANGELOG.md` diff that cannot reach this code, which passed on rerun with no changes. The cause was two clocks of different resolution being compared as one: the test took `cycleStart` from `time.Now()` (nanosecond-precise) and then asserted that a marker created immediately afterwards was *newer*, but `recheckMirrorPending` reads `info.ModTime()`, and Linux fills inode times from `ktime_get_coarse_real_ts64`, which advances only once per timer tick (1-4ms at typical `CONFIG_HZ`). A marker minted microseconds after `cycleStart` gets an mtime rounded DOWN to the tick boundary, which can land *before* it — so the verdict took its `Before(cycleStart)` branch and returned the survived-the-clear error instead of `again=true`. The fix is entirely in the fixture: a new `filesystemNow` test helper stamps a scratch file in the marker's own directory and returns its `ModTime`, so both sides of the comparison are drawn from the one clock that actually stamps markers. Because that clock is non-decreasing and truncation applies to both readings alike, "the marker was created after `cycleStart`" now holds by construction at any tick rate, rather than by luck inside a one-tick window. `recheckMirrorPending`'s `Before(cycleStart)` comparison is deliberately UNCHANGED: the same tick-boundary skew exists in the real mirror loop, but there its consequence is a conservative stop that the next mutation's own claim recovers, and the error branch is load-bearing — it is what stops an unclearable marker from cycling forever. Relaxing it to a tolerance window would have traded a flaky test for a weakened invariant. (links-testing-tt0c.4)

- This machine now enumerates its own checkouts, which is the claim predicate's liveness leg made real: delete a worktree mid-claim and its lane is free on this machine's very next derivation — no waiting out the freshness window, no cleanup command, nothing of lit's running at removal time — while a second clone, which cannot see this filesystem, keeps reading that lane as held until the window lapses. **The asymmetry is the honest one: deletion is a local fact, and only its owner can observe it instantly.** The enumeration asks git (`git worktree list --porcelain -z`, which raises the project's git floor to **2.36**) rather than listing `<git-common-dir>/worktrees`, and the difference is not academic — a worktree deleted with `rm -rf` instead of `git worktree remove` leaves its private git directory, token and all, sitting under the common dir until somebody prunes, so a directory listing would report a checkout that has been gone for months as alive. Git calls that record `prunable`, and inheriting git's judgment is the whole answer. It inherits the other half too: a worktree that has been explicitly **locked** is one git refuses to call prunable even while its directory is missing — removable media, an unmounted share — and a checkout git lists as live but whose identity cannot be read fails the entire enumeration rather than being dropped from it, because dropping it is not "we skipped one", it is this machine asserting the checkout is deleted and voiding a live claimant's evidence on the strength of an error it declined to mention. **Absent is not dead.** A checkout that has only ever run read-only commands holds no token at all, is enumerated as live, and contributes nothing to the token set — it has produced no work events, so it can hold no claim, and reading its silence as deletion would be the same mistake in the opposite direction. Nothing is stored and there is no worktree registry: identity lives in the private git dir precisely because git creates and destroys it with the checkout, so the prune reads that fact live at the moment of the query and throws the value away — a registry would be a second representation of something git already owns, and it would outlive the worktrees it described. This is filesystem enumeration, not process liveness; no heartbeats and no probes, a family the design rejected and that stays rejected. Scope is the workspace id, and it is load-bearing for privacy as much as for correctness: a different clone of the same repository on this same machine carries a different workspace id, is never pruned by this store's enumeration, and ages out exactly as a remote machine's claims do. The same pass doubles as the local address book — each token paired with its worktree path and branch, empty for a detached HEAD — produced here and written nowhere, so paths stay on the machine that owns them; rendering them is the visibility work that follows. **`-z` is load-bearing, not tidiness.** A newline is a legal byte in a POSIX path and the newline-terminated format emits paths raw, so a worktree at a path ending in the literal bytes `\nprunable` produced a record whose second *line* was the word `prunable` — read as an attribute of the live record it had just opened, which was then dropped from the enumeration with no error at all, voiding that checkout's claims silently. `\nbare` did the same and `\nbranch <ref>` corrupted the address. The remedy is the delimiter and not a check: the newline-terminated format is ambiguous *by construction* for these paths, which is why git grew `-z`, so a parser reading it is guessing however carefully it is written. Under `-z` the path is one NUL-terminated field with its newline intact and there is no ambiguity left to detect. Nothing consumes any of this yet — selection and display each follow — so no command behaves differently today. (links-claims-1ihf.4)

- Lane claims are now derived — who is working what, computed from the work records the database already syncs, and stored nowhere (design-docs/work-claims.md). A lane is held by a checkout when four things hold at once: the lane is unfinished, that checkout produced the latest *establishing* event in it, the claim is fresh, and the checkout is live as far as this machine can tell. Nothing consumes this yet — selection, display, takeover and the sync report each follow — so no command behaves differently today. **A derived claim cannot drift from the evidence, because it is a reading of the evidence**, which is why there are no claim rows, no cache, no lifecycle and nothing to clean up; a test drives the whole read path against a real store and fails if the commit at HEAD moves or a single table comes back dirty. **Only starting and completing a ticket take a lane.** Closing one unfinished, reopening, archiving, deleting, and every plain field edit can refresh a claim that already exists but can never create or transfer one, so a drive-by comment or a grooming pass from another checkout cannot capture an epic somebody else is deep into. The narrow reading is the right one wherever the design leaves room, because the two mistakes are not symmetric: a verb wrongly treated as establishing routes every other stream away from real work, while a verb wrongly treated as non-establishing only leaves a lane unclaimed — which is exactly how the tool behaved before claims existed. That classification is a map over the sealed action set rather than a switch with a default arm, so a ninth lifecycle verb fails a test naming itself instead of being silently answered on its author's behalf. **Two ways for the latest establishing event to name nobody, and they point in opposite directions.** An *unattributed* event — the common case on any repository with history, since attribution is historical fact and is never backfilled — says somebody took this lane and the record does not say who; the derivation stops there and reports the lane unclaimed, because reading past it to an older attributed ancestor would not be the best available answer but an answer we have positive evidence was superseded, handing the lane to a checkout that demonstrably walked away from it, more confidently the older the repository gets. A *void* event, from a checkout this machine has enumerated its worktrees and proven gone, is disproven rather than unknown: we know exactly who produced it and we know they are absent, so the lane genuinely reverts to whoever else has standing. Unknown stops the search; disproven falls through. **The claimable unit is the lane, because the lane is already the system's declared unit of serialization** — an epic that declares none is exactly one lane rather than a special case, a deliberately multi-lane catch-all epic is claimable line by line so one started bug never monopolizes twenty independent ones, a parentless ticket is its own lane, and pulling a cross-epic dependency onto a stream's path produces evidence in that ticket's own lane rather than swallowing the neighbouring epic. Freshness is measured from the holder's last mutation of any kind, not from the establishing event, so ordinary working commentary carries a claim through a long stretch on a single ticket; past the window (`claims.freshness_window`, default 24h, per-repository, validated positive where config is read) the lane is available again but keeps its provenance, because "last touched by 7f3a three days ago" is a different offer from "nobody has ever worked this". A second checkout with its own live establishing evidence is reported as *contested* rather than hidden, and contest changes no routing: the latest establishing event still holds, and the annotation exists so both sides can be told. Contest requires an establishing act for the same reason a claim does — under the looser reading every lane anyone had ever glanced at would report as contested, and an annotation that fires constantly is one nobody reads. **Deleting a checkout is a local fact and only its owner can observe it instantly**, so the liveness leg is a value the caller supplies rather than a callback it might forget to fill in, and the zero value is a machine that has enumerated nothing and therefore prunes nothing — the "where uncheckable, assume live and let freshness govern" default, reachable only by saying nothing. The acceptance grid drops each of the four legs in turn and watches the claim dissolve, and each leg was verified by deleting the rule from the implementation and confirming which row noticed. (links-claims-1ihf.3)

- Every work mutation now records which checkout produced it. Each `issue_events` row carries an attribution pair — the producing checkout's opaque stream token plus the opaque workspace id it was produced under — and that pair is the entire shared-data footprint of work claims (design-docs/work-claims.md). Nothing derives claims from it yet; the predicate that reads these stamps follows. **"Every mutation" is a property of the write path, not an obligation on call sites.** `recordEvent` is already the single insertion point for issue history, and its four callers are all internal, so the stamp is read off the store rather than passed in — which is why adding a mutation command in future cannot forget to attribute it, and why no input struct grew a field. The store learns its identity from `app.Open` immediately after that identity is resolved; identity is deliberately not an `Open()` parameter, because resolving it *after* the store opens is what makes a command that cannot reach its store mint no identity at all. `app.Open` is not the only opener — sync commands, workspace recovery, adopt, the upgrade path and cross-project reads each open a store their own way — but it is the only one whose store records *new* events; the others read, or replay a dump, and replay preserves the producer's attribution rather than stamping its own. **A pair is complete or it is absent — there is no half.** A stream token with no workspace to scope it identifies nothing (two checkouts of different clones may hold the same token without colliding), and a workspace id with no stream names no checkout, so one constructor admits exactly those two results and every route into a populated pair goes through it — the write path, the read path, and JSON decoding. The halves are unexported to make that list exhaustive rather than merely current: a sync file or backup is bytes lit did not write, and a hand-edited one carrying `{"stream":"x"}` with no workspace would otherwise restore into a stream id scoping no workspace — invisible to the model, which reads it back as absent, but plainly there to `lit doctor`, to dolt tooling, and to every future migration. Decoding collapses it to the absent pair instead, and the collapse is quiet rather than an error because "unattributed" is a state that is already legal and meaningful everywhere, so nothing is skipped and no operation is abandoned. That is what lets `app.Open` hand its token over unconditionally instead of branching on whether one exists: a read-mode open in a never-mutated checkout passes an empty token and its store stamps nothing, which is the behavior wanted anyway. **Cold start is the schema's doing, not a migration's.** Both columns are nullable and nothing is backfilled, so events written before this release carry SQL `NULL` — distinct from the empty string, and read back as "this work has no producer" rather than "this work was produced by the empty checkout". A freshly upgraded repository therefore derives zero claims and selects work exactly as it did before, with no upgrade step to run and no window where it behaves differently. **Attribution is historical fact, so restoring a dump replays it rather than re-stamping it**; a restore that substituted the restoring checkout's own pair would rewrite the whole backlog's history into a claim for whoever happened to run it, and preserving it is also what keeps an export/import round trip lossless. Both halves stay opaque: the database syncs to shared remotes, so nothing user-, host-, or path-shaped enters these columns, and resolving a token to a physical checkout happens only on the machine that owns it. The acceptance test drives two clones through the real CLI over a real git remote and fails unless the second one sees the first one's exact pair — asserting the pair rather than merely its presence, so adoption re-stamping inherited history would break it — then has the second clone do its own work and pins that the two are distinguishable in the one shared backlog. (links-claims-1ihf.2)

- Each checkout now mints its own opaque identity — a 13-character token in the worktree's private git directory — on its first mutating command. This is the identity half of work claims (design-docs/work-claims.md); the entry above carries it onto work events. **Identity is keyed to the checkout, not the session**, which is the whole point: a token keyed to a session dissolves on every restart, rebuilding the amnesia the claims design exists to end, while a token keyed to the checkout means a fresh agent session in a worktree inherits that worktree's stream with no re-briefing. **The lifecycle is git's, not lit's.** The store is derived from `--git-common-dir`, which answers with the same directory from every worktree, so all of them share one backlog; identity is derived from `--git-dir`, which answers with a different one per worktree (`.git` in the primary clone, `.git/worktrees/<name>` in a linked one). Git creates that directory with the worktree and removes it with `git worktree remove`, so an identity is created and destroyed by the same commands that create and destroy the checkout — no registry of live worktrees, no cleanup path, nothing left behind. **A read-only command in a never-mutated checkout mints nothing**, and that holds structurally rather than by anyone remembering it: the access mode every command already declares in the registration table now selects the identity contract alongside the store contract, the two paired in one record, so a mode cannot open the store read-only and still mint — and a mode added later cannot supply one behavior and silently inherit a default for the other. **Write-once is the kernel's job, and so is completeness.** Two mutating commands starting together in one fresh checkout both see no token and both go on to publish one; exactly one wins, and the loser adopts the winner's token instead of failing. The token is written and flushed to a temp file in the same directory and only then given its real name with `os.Link`, which fails when the destination already exists — so an incumbent identity is never replaced, and the token file holds a complete token from the first instant it is visible anywhere. `os.Rename` would publish just as atomically and silently overwrite an existing identity, which is the one thing this must never do. **The obvious approach has a window that bites twice.** Creating the file at its final name and filling it afterwards makes the directory entry visible before the bytes: a concurrent command reads the empty file and rejects it as damaged, and a process killed in that window leaves an empty file that nothing can replace — permanently failing every later command in that checkout, read and write alike. A process killed mid-staging leaves its temp file behind, which is accepted rather than reaped: a reaper would delete exactly the file a *concurrent* first mutation is about to link, turning a harmless orphan into a failed command, and the staging path runs only while a checkout has no identity at all, so the litter is bounded by kills inside one checkout's first mutation. Only the exact token name is ever read, so a leftover cannot be mistaken for an identity. Where hard links are unavailable altogether — some network mounts, FAT-family filesystems — publishing fails with an error naming that cause rather than an opaque `link: operation not permitted`; it does not fall back to a weaker publish, because an atomicity guarantee that varies by filesystem is one nobody can reason about. Absence and damage stay distinguishable throughout: no file means "nothing has mutated here yet" and yields no identity, while a file that is not a token fails loudly and names its own remedy, since deleting it is the whole fix. It is never healed automatically, because quietly minting a replacement would give a second identity to a checkout whose first may already be attached to work. The token is eight bytes of `crypto/rand` in unpadded lowercase base32 and carries nothing about where it was minted — no path, no hostname, no username — because it is bound for a database that syncs to shared remotes and that this project publishes. (links-claims-1ihf.1)

### Fixed

- `lit next` and `lit backlog` no longer fail outright on any repository that has ever soft-deleted or archived an issue that carried events — which is to say, almost any repository old enough to have one, this one included. Claim derivation's evidence gather read issues through the zero-value `ListIssuesFilter{}`, which excludes both, while it read *events* through `ListAllEvents`, which excludes neither; the first deleted or archived issue with any history at all then failed `claims.NewEvidence`'s completeness check — correctly, since an event naming an issue the read never supplied is exactly the gap that check exists to catch — and took every `next`/`backlog` invocation down with it. The fix widens the read (`IncludeArchived: true, IncludeDeleted: true`), matching `internal/store/import_export.go`'s own full-read filter and the completeness `claims.Evidence`'s own doc comment already demanded: claim derivation needs every issue an event could name, closed ones included, because a checkout's hold on a lane can rest entirely on a `done` against a ticket no longer open. Introduced alongside claim routing (links-claims-1ihf.5) and caught while building the claim-annotation surface for `lit backlog`/`lit next` (links-claims-1ihf.6), which is the first work to run that evidence gather against this repository's own backlog.

- Two embedded-Dolt engines can no longer data-race each other while being constructed in one process. Constructing an engine writes package-global state in the dolt stack — go-mysql-server's `InitStatusVariables` rewrites the process-wide status-variable table, and `NewSqlEngine` re-points the global binlog-consumer singleton — so any lit path that opens two stores concurrently in one process raced at open, even with the databases at unrelated paths. The race had no reachable trigger in shipped commands, which open one store at a time, but it was one refactor away on the cross-project rollup and fired instantly once the store test suite ran in parallel: `go test -race` reported 145 warnings, every one at construction and none during query execution. That distribution is the fix's shape: a mutex in the vendored driver (patch 5 in `internal/vendor/dolthub-driver/README.lit-patch.md`) serializes construction at the one funnel every engine passes through, and constructed engines run concurrently exactly as before. (links-testperf-xxsx.2)

- `lit backlog` and `lit next` no longer spend seconds inside the SQL analyzer before reading a single row. The batch relations query asked for every edge touching the workable set as `(src_id IN (…) OR dst_id IN (…)) AND type IN (…)`, and that cross-column OR is what made the whole command's cost track the backlog's size: no index covers both endpoint columns, so the engine's costed-index analysis had to represent the other column's disjuncts as unbounded ranges on every candidate index, and its overlap-elimination pass then performed quadratic collation-aware string compares across the blown-up range set — pure planning work, before execution began, repeated for each of the pipeline's relation queries. At 55 workable tickets that was ~5.5s of a ~5.7s command; the same command now completes in ~0.2s with byte-identical output. The query is split into one query per endpoint column — each a conjunction of point lookups the planner handles linearly — merged and deduplicated in Go, with created-at ordering preserved and ties broken deterministically by primary key, which the single SQL ordering never guaranteed.

- A slow command can no longer re-arm the automatic receive on every invocation. The inline receive after each command is debounced so a burst pays at most one fetch per interval, but the 10-second interval only bounded anything while commands finished well inside it: once the analyzer regression above pushed a read command past 10s of wall clock, the debounce was always expired by the next command, and every command in a session paid the full ~7s fetch-and-compare against a remote that was almost always already up to date. The interval is now 5 minutes — receive freshness is a minutes-scale concern, and a bound on background work must hold regardless of how long the foreground takes.

### Changed

- Opening an existing workspace no longer replays its own creation. Every write-capable open — `Open`, `OpenSync`, and `lit init`'s `EnsureDatabase` — funneled through a bootstrap that unconditionally constructed two throwaway embedded-Dolt engines before the real one: the first to run `CREATE DATABASE IF NOT EXISTS` against a database that has existed since the workspace's first day, the second to check that the default branch is named `master`. Engine construction is the expensive part of an open and is process-serialized (vendored-driver patch 5), so every write command paid two-thirds of its engine constructions re-answering a question whose answer never changes; on the development machine that bootstrap was ~78ms of a ~116ms open of an existing store, and is now a single `stat` (~20µs). **The branch check still runs on every write open — it moved, it did not die.** It was never really a creation-time rule: an adopted clone arrives pre-made on whatever branch its remote had, and it was the *next* open's bootstrap that renamed it to `master`. That duty now runs on each write open's own engine: `Open` runs it inside the commit-locked startup it already holds for migration, and `OpenSync` reads the branch state lock-free and takes the commit lock only when a rename is actually due — so a pre-made database is still normalized at exactly the moment it was before, while read-only `OpenSync` consumers (`lit sync status`, every mirror cycle) never queue behind a snapshot copy's minutes-long commit-lock hold for a no-op — the enforcement site changed, the contract did not, and three tests pin the new one: the updated `EnsureDatabase` test proves the bootstrap leaves a pre-existing database untouched and the first write open lands it on `master`, `TestOpenSyncNormalizesPreMadeMainBranchToMaster` proves the mirror-side rename actually fires, and `TestOpenSyncOnNormalizedStoreIgnoresHeldCommitLock` proves the no-queueing liveness claim — an `OpenSync` on a normalized store completes while another holder owns the commit lock. Creation itself — the only case that needs the bootstrap — still runs the full path, including its branch normalization. (links-testperf-xxsx.3)

- Store tests now obtain a migrated database by copying a template instead of building one from nothing, which is where the suite's broad fixture tax lived: essentially every one of the 388 tests opened a fresh embedded Dolt database and brought it up through the migration chain before asserting anything — ~390ms of admission per test, growing with every schema change. Each test binary now builds one template store via the real `Open` (so the fixture cannot drift from what `Open` produces — it *is* an `Open` artifact) and hands each test a private directory copy: ~6ms for the copy, ~40ms for the open, and one engine construction instead of three through the process-wide construction queue, so the win compounds under `t.Parallel()`. Measured serially on the development machine, the suite's per-row cost drops from the epic's 474s to 146s, and the median row from 0.45s to 0.06s; the 92 rows still at or above 0.5s are the giants the epic's other children own, not fixture tax. **There are two templates, not one, because copies of a single template share its root commit.** Production workspaces are created independently and have unrelated Dolt histories — the shape the sync engine's unrelated-history handling exists for — so a two-workspace sync test seeding both sides from one template would silently slide onto the related-history path while staying green. Each side draws from its own independently built template, and the builder fails loudly if the two templates ever share even one commit, checked against the whole log rather than the heads because a shared root is a merge base even under distinct heads. The isolation invariant the ticket demanded is enforced twice and proven once: the template's files are frozen read-only, so a test that accidentally opens the template path itself fails at its first write instead of poisoning every later copy, and a residue test writes through one copy, then asserts the next copy is pristine, schema-identical to a from-scratch store, and that the template's bytes did not move — each layer carried by its own test — `TestFrozenTemplateRefusesDirectOpen` proves a direct open of the template path fails and leaves its bytes untouched, and `TestFixtureResidueCannotCrossCopies` proves nothing crosses between copies — and both were additionally verified by mutation (share the template: the freeze refuses the open; share one copy: the residue test names the leaked issue). - `TestOpenForReadPendingMigrationUnderJournalHolder` — the suite's second-slowest test at 29.7s — now runs in 0.8s, and the profile that got it there indicts a different budget than the epic's notes had guessed. The test pins that a read open needing a migration while a snapshot copy holds the journal lock fails with the retry-after-holder guidance and heals once the holder releases; 29.2 of its 29.7s were spent inside the failing open, and not in the engine-open retry (`engineOpenRetryMaxElapsed`) previous investigation had blamed — read opens configure no open-retry backoff at all, and Dolt's own journal-lock wait is 100ms before its read-only fallback. ## [0.7.0] - 2026-08-23

### Changed

- A fold of a long local chain — the shared-history field-aware reconcile, the unrelated-history `lit sync reconcile combine`, and `lit sync reconcile take local`, all three of which drive the same replay — no longer holds the whole backlog in memory once per folded commit, nor rewrites every table to express what each commit changed. Measured on the development machine, folding 102 commits over a 400-issue backlog drops from 26.1s to 5.3s and from roughly 21 GiB of allocation to 1.5 GiB. At the scale the new acceptance test pins — 502 folded commits over a 1000-issue backlog — the same machine measures about 70 seconds and 83 MiB of retained-heap growth, and quadrupling the chain there, from 127 commits to 502, moved that peak by 1.22x rather than by 4x. The test asserts neither figure: it runs that one scale point and fails if the combine exceeds ten minutes or grows retained heap past 160 MiB — a memory bound placed between the streamed cost and the materializing one, so that ordinary variance cannot fail it and a reintroduced materialization cannot pass it. **Two costs, two causes, and the obvious one was the smaller.** Reading the backlog at a historical commit is a `DOLT_RESET --hard`, which moves whichever branch it runs on, so a replay that read and wrote on one scratch branch had to finish every read before its first write — and carry every projected export across that boundary. The replay now runs on a *pair* of scratch branches: history is read on one, the spine accumulates on the other, and Dolt's per-branch working sets keep either from seeing the other's uncommitted rows, so one projected export is alive at a time. That is the memory fix, and on its own it would have left most of the runtime alone. Measuring first is what showed why: the wholesale clear-and-rewrite per step was 87% of the elapsed time, because a folded commit touching one issue was rewriting all 400 rows to say so. Each step now writes only the rows that differ from the step before it. Time still grows with chain length times backlog size — every step still reads the whole backlog at its own commit — but the constant is far smaller.

- **A delta is only as good as its account of what a delete drags away.** Every child table cascades from `issues`, so which comments, labels, events and relations are still live is not what the previous export says; it is what that export says minus everything hanging off an issue the delta is about to delete. A relation spanning a rewritten issue and an untouched one disappears with the rewrite and has to come back. `relations` also carries `created_at` and `created_by` outside its `(src_id, dst_id, type)` primary key, so two rows can share a key and still differ — the diff compares whole values and deletes by key, which catches that. The `issues` table needs the mirror-image care, for the opposite reason: a `model.Issue` is a hydrated *view*, carrying labels denormalized from another table and, for an epic, a lifecycle composed from every child — and none of those is an `issues` column. Comparing whole values called a row changed whenever a label moved or any child of an epic changed state, then dragged that issue's entire cascade through a rewrite to express nothing at all; the diff compares the persisted row the `INSERT` binds, so adding a label now touches the labels table and leaves the issue alone. The wholesale rewrite stays for restores, where the caller genuinely cannot know what the tables hold: it clears them and then applies the same delta from empty, so the restore-and-replay path's `INSERT` statements each live in exactly one place, shared with the delta — the ordinary creation commands (`CreateIssue`, `AddComment`, `AddLabel`) keep their own creation-time statements, so this is sole ownership of the whole-row write path rather than of the table. A test walks both paths down two stores through the same sequence of backlog states and fails if their exports ever disagree. One further thing has to hold before a diff of whole values means anything: the same rows must read back the same way twice. An event carries its field changes as a slice, and the query loading them ordered the events but not the change rows joined onto each one — so an event nothing had touched could compare unequal to itself and be rewritten to say nothing. That read now sorts by the change's field, which its primary key already makes a total order.

Licenses are found at any depth and by two routes — a file whose name says it is one, and any file inside a directory named `licenses/`. The second route is not redundant: `github.com/golang/freetype`'s root LICENSE is a pointer document that no classifier can match, and its actual GPL-2.0 text sits at `licenses/gpl.txt`, a name no license-shaped filename pattern reaches. Findings are grouped by what a reader must do about them — a module's own root grant (what a scanner resolving `module@version` reports) separately from texts nested in its tree (what a file-walking scanner flags), unclassifiable files in their own section, and modules under a `replace` directive listed whether or not their license is permissive, because the go tool reports the *original* path and version against the *replacement's* directory and that divergence is itself the finding.
- Degraded sync state now reaches the OWNER out-of-band, not just whichever agent runs the next command. A new `sync.owner_notify_cmd` config setting (empty by default) names a shell command — e.g. a `curl` to an ntfy topic — that lit runs at detection time, with the event's facts in `LIT_NOTIFY_KIND`/`LIT_NOTIFY_SUMMARY`/`LIT_NOTIFY_REMOTE`/`LIT_NOTIFY_BRANCH`/`LIT_NOTIFY_REPO`, whenever a surface detects a real divergence (no common ancestor, a reconcile that could not converge, a held prose conflict) or a push attempt completes failed — the inline auto-receive, `lit sync pull`, the explicit reconcile, `lit doctor`'s persistent-divergence escalation, and the one shared push path all feed it. Notifications de-duplicate per episode via per-kind `owner-notify.<kind>.last` markers: the first detection fires immediately, the same persisting condition re-pings at most daily, and a resolved condition (a landed push, a converged reconcile) clears its marker so the next occurrence fires immediately again. A failed hook is loud on stderr, recorded in `traces/sync/`, and retried on the next detection rather than silently marking the owner informed; `LIT_DISABLE_AUTO_SYNC=1` suppresses the hook along with the rest of automatic sync. In the links-sync-pgct field incident the owner learned of a week-old fork only because duplicated work happened to get re-ordered and a session went digging — this is the channel that makes the fork the owner's news the day it forms.
- `lit sync reconcile take local|remote` — the resolution that permanently discards one side's unique issues — now refuses to run without the owner's explicit approval. Run bare it exits 5 with a refusal block naming exactly which issues the take would destroy (the both-sides inventory), pointing at the approval-free alternative (`lit sync reconcile combine`, the union that keeps every issue and stays agent-runnable), and carrying a one-time `--owner-approved` token; only a re-run with that token performs the destruction. The token is a digest of both heads and the chosen side, checked inside the store under the same commit lock that mutates — so any commit landing on either side after it was issued, or presenting a take-local token to take-remote, voids it and re-mints a fresh one for the fork as it now stands (the prose-resolve fingerprint device at whole-backlog scope). Every gate refusal and every approved take is durably traced. This closes the incident's near-miss: an agent alone at a no-common-ancestor fork was offered 'take local' / 'take remote' — two destroy-a-side options resolved safely only by luck; now the party who can lose the work is the party who authorizes the loss.
- The push-failure staleness banner now reaches sessions that only run mutating commands. Every push attempt — the on-change background mirror and the explicit `lit sync push` alike — records how it ended (pushed, skipped and why, or failed and why) in a `push-outcome.last` marker in the workspace's storage dir, written by the one shared push path so the marker and the durable `traces/sync/` record can't disagree. Every mutating command (`new`, `start`, `update`, `close`, `comment`, `rank`, …) then prints a `sync: automatic push … is FAILING` banner after its own output whenever the last attempt failed, plus the existing stale-fetch warning — wired once at the command dispatch seam, so a mutating command added tomorrow is covered without remembering any call. Previously the banner was wired into exactly three read commands (`lit backlog`/`next`/`show`), so an agent session chaining `new → update → close` against a dead remote — a completely ordinary agentic pattern — saw nothing on any command it actually ran while the failures piled up in `mirror.log`. The mutating-side banner deliberately keys on "the last push attempt failed", not the read commands' ahead-count: a mutating command is always momentarily ahead at its own end (its mirror pushes only after the process exits), and an ahead-based banner there would warn on every healthy mutation and train its readers to ignore it. The read commands lead with the same failure line when it applies (the ahead-count line shows the accumulating effect; this names the cause), and `lit doctor` now surfaces the failure's reason plus the mirror worker's log (`mirror.log` path and last-write age) — previously a durable failure sink no command ever pointed at.
- `lit backlog`, `lit next`, and `lit show` now print a `sync:` warning line up front when unpushed/unfetched state has drifted, instead of that only surfacing on request via `lit doctor`. Two independent conditions trigger it: local is ahead of the remote by unpushed changes (`lit sync push` to fix), or a fetch against the remote hasn't succeeded in over 24h (`lit sync fetch` to fix) — tracked by a new `fetch-success.last` marker in the workspace's storage dir, stamped by every real successful fetch (`lit sync fetch`/`pull`, the reconcile command's pre-reconcile fetch, and the inline auto-receive), distinct from the existing debounce marker so a remote that keeps failing every fetch attempt still reads as stale. A workspace with no remote configured stays silent for both conditions; a workspace already mid-divergence (which already gets the heavier `SyncFailure` escalation from the reconcile machinery) suppresses only the unpushed-ahead condition — the stale-fetch condition is independent and still fires. This closes the other half of the links-sync-pgct field incident: 25 local changes and a fresh, never-synced clone both sat unnoticed for days because nothing surfaced drift on the commands actually run day to day.
- `just build` now stamps `internal/version.{Commit,Date}` via `-ldflags`, computed locally (`git rev-parse --short HEAD`, the local clock — no network call) through the new `scripts/version-ldflags.sh`, which `scripts/install.sh`'s source mode now shares too. `lit version` reports the real commit and how long ago the binary was built instead of unconditionally "commit unknown, built unknown", and warns when a binary is older than `internal/version.StaleBuildThreshold` (7 days) — the previous silence made a stale local binary look identical to a fresh one, which is the suspected root cause of the links-sync-pgct field incident. `just build` deliberately leaves `Version` unstamped so ordinary local builds stay `IsDev == true`, preserving the guard that keeps a stray dev build from overwriting a real release's downgrade stamp.
- Dev-build status now surfaces proactively instead of only on request via `lit version`. `lit doctor` prints a `build:` line naming whether the running binary is a dev or release build, and — for a dev build — how long ago it was built, flagged `STALE` past `internal/version.StaleBuildThreshold`. `lit init`'s phase-boundary output names the same status the moment it commits to a "start fresh" decision (no remote backlog to adopt) or reports an adopt failure or success. Every sync-failure block (`lit sync pull`/`push`/`reconcile`, and `lit doctor`'s persistent-divergence exit) names it too, since a stale local binary silently missing a landed fix was the suspected root cause of the field incident this epic exists to prevent — naming the build status at the moment of failure turns a mysterious divergence into a five-minute diagnosis instead of a second `lit version` round trip.
- Every sync/init decision — `lit init`'s remote-adopt outcome and each `lit sync fetch`/`pull`/`push`/`reconcile` action and its result, including the on-change push mirror and the inline receive/reconcile that runs after an ordinary command — is now recorded unconditionally as a durable JSON record under `traces/sync/`, alongside the existing `traces/automation/` `lit doctor` already points at via `traces_dir`, using the same `internal/trace` writer `internal/workflows` already uses for firing traces. Previously the only durable trace (`traces/automation/`) fired solely when `LNKS_AUTOMATION_TRIGGER` was set, so a directly-run interactive `lit init` or `lit sync` command — and the inline auto-receive/reconcile that runs after nearly every ordinary command, since nothing sets that trigger for it — left no record anywhere once the process exited. This was the missing evidence trail behind the links-sync-pgct field incident: the divergence was found only because an agent happened to go digging mid-session. Each record's `trigger` field is empty for an interactive occasion and names the trigger for an automated one, so the new unconditional trace and the existing automation-gated trace can never disagree about what fired a given occasion; the automation-gated trace and its consumers are unchanged.

### Changed

- lit's lock discipline is now declared in one place — `internal/filelock`'s package doc — instead of existing only as consistent-but-unwritten practice: owner exclusion is an flock through `filelock.Acquire`, with "is the owner still alive" answered only by exclusive acquisition (never an mtime, a PID probe, or a wall-clock threshold) — the declared rule, and as declared not yet a universal fact: the mirror-pending marker's age-out predated it and was named in the doc as being rebuilt onto it (links-locking-il18.4) — rebuilt within this same release by its own entry below, so no straggler remains; as declared, the doc also named the commit lock's `O_EXCL` create with PID/mtime staleness, likewise rebuilt within this same release by its own entry below; the acquisition order, outermost to innermost, is workspace → Dolt's own `.dolt/noms/LOCK` → commit → snapshot producer beacon (as declared it carried an engine slot between workspace and LOCK — the engine-lock retirement below removed that slot within this same release; the sync-push lock sits outside those slots, only ever taken as a non-blocking probe, so nothing can wait on it — as declared it was also called outermost in practice, a designation the mirror liveness beacon below now carries instead, sitting outside even the sync-push lock); and lit-minted lock files sit beside the dolt directory so a `lit snapshots restore` that rotates the directory cannot move them out from under acquirers, with the placement exceptions (the snapshot producer beacon inside `snapshots/`; the adopt-pending marker — a condemnation record, not a lock — inside the dolt root; Dolt's own LOCK inside the dolt directory, being Dolt's file) each stating its reason where its path is minted. Writing it down surfaced one fact no call site shows: Dolt's LOCK is acquired by the embedded driver when a write engine opens and held for the Store's whole lifetime, so taking it while holding the commit lock inverts the order against every live write Store and can deadlock. The doc records the rule (take it before commit or not at all) and the one tolerated deviation, the mid-mutation GC-contention reconnect, with the bounded-wait reason it cannot wedge (as declared, the deviation also covered Open's then-lazy first engine open at migrate; the retirement below made write engines open eagerly before the commit lock, narrowing the deviation to the reconnect). This is the declaration the rest of the links-locking-il18 epic lands against.

- `lit` no longer links `github.com/hashicorp/golang-lru` — either major version, both MPL-2.0 — anywhere. The two coordinates arrived through exactly eight files lit never wrote: seven in Dolt (`store/nbs`, `libraries/doltcore/doltdb`, `libraries/doltcore/remotestorage`) importing v2, and go-mysql-server's `sql/cache.go`, the single file that put v1 into the binary. Both forks now import `github.com/promptctl/primitives` instead — `lru` (generic) in Dolt, `lruany` in go-mysql-server — a new org-owned, MIT, stdlib-only module whose cache packages were written through the clean-room protocol in `design-docs/clean-room-reimplementation.md`: four sequential agents, only a behavioral spec and then reviewed tickets crossing the wall, the implementer sandboxed away from the original's source, and the whole record — what was read, the sandbox verdicts, every ruling and known divergence — in that module's `PROVENANCE.md`, audited before integration by an agent that was never behind the wall. In Dolt the swap is an import rewrite alone, because the replacement ships the replaced method sets exactly; in go-mysql-server it additionally touches the two `lru.New` call sites, the one behavioral change: they discarded the constructor's error and now panic at construction — at the call that owns the bad size — instead of failing at first use, far from the cause. Performance was measured, not assumed, at one pinned shape on both sides (8 goroutines, one shared instance, 90% Get / 10% Add, capacity 1024 against a 4096-key working set, medians of three 3s runs): the original measured 204.5 ns/op (`Cache`) and 263.0 ns/op (`TwoQueueCache`); the replacement, fetched as the published `v0.1.0` the build actually links, 190.4 and 199.6 — faster on both types, zero allocations per operation on both sides. The vendored `dolthub/driver` module and the Dolt fork each gained a `replace` mirroring the top-level fork pins so that, resolved standalone, neither re-records a golang-lru coordinate through an upstream go.mod; inside lit's build those replaces are inert. The freshly generated `LICENSE-REPORT.md` and SBOM now carry no MPL-2.0 row at all — 155 components, down from 156 on the then-current master (two coordinates out, one in; that 156 already reflected the go-sql-driver removal below, which merged first, and the buzhash cut below later took the count to 154) — and `go run ./tools/licenses -graph` finds neither coordinate in the module graph. What remains of the name in go.sum is two `/go.mod`-only hash lines (v0.5.0/v0.5.1, ancient `go.opencensus.io`-era graph ancestry): they carry no source hash and ship no code — a milder residue than the freetype entry, which does carry a source hash and ships its GPL text, though both belong to the same graph-cleanup ticket.
- `lit` no longer depends on `github.com/go-sql-driver/mysql` (MPL-2.0), in any module, at build time or test time. The coordinate was carrying exactly two fields — a MySQL server error code and a message — across a package boundary between two modules lit already owns on both ends: the vendored `github.com/dolthub/driver` constructed that project's `*MySQLError` in `translateError`, and `internal/store` asserted the same type to recognise error 1146 and read a pre-goose commit as schema 0. The driver now defines its own `MySQLError` and the store matches on that, so the removal is a single change with both halves in it — replacing only the consumer would have left `errors.As` silently failing to match, `isMissingTableError` returning false for a genuinely missing table, and nothing failing to compile. The type was written from the MySQL protocol and from what those two call sites actually need, not from go-sql-driver's source: `design-docs/clean-room-reimplementation.md` makes rewrite this epic's default, and a shape partly dictated by a wire protocol is still not ours to copy out of an MPL-2.0 file. It carries no SQL state, because nothing produces one and nothing reads one. Its rendering, `Error <code>: <message>`, was not a free choice — seven existing assertions in the driver's own smoke tests already pinned it, and they pass unchanged. Two test-only dependencies went with it, since a test-only requirement is still a line in `go.mod` and still a row an auditor reads: upstream's MySQL-comparison mode in `smoke_test.go` (a hardcoded `runTestsAgainstMySQL = false` plus seven `if`/`else` sites and a swap to a `localhost:3306` server this repo never provisions — dead in every run, and the `else` arms unreachable), and `gorm_test.go`, which was the sole surviving path to the coordinate via `gorm.io/driver/mysql` and tested an ORM integration lit uses nowhere. Every other test in the driver's suite remains and still runs. MPL-2.0's count in the link closure drops from 3 to 2 — the remaining two were the golang-lru coordinates, whose removal (recorded above) later took it to zero. The coordinate's full hash rows do remain in both go.sums, kept for the dependency test graph — the dolt fork's binlogreplication tests import the driver — so an auditor reading go.sum still meets the name there: not linked, not buildable from lit, and owned by the graph-cleanup ticket alongside freetype.
- `lit` no longer depends on buzhash under either of its two coordinates — `github.com/kch42/buzhash` (linked into the binary) and `github.com/silvasur/buzhash` (go.mod/go.sum only), the same 2016 code published under the author's account before and after a rename, both carrying a hand-written, profane WTFPL variant that no classifier matches, so both classified as Unknown: under this epic's bar the worst row a report can hold, because an auditor cannot even say what it permits. Neither was doing anything. Dolt's write path chooses chunk boundaries with `keySplitter` — a key-hash against a Weibull-modelled threshold, no buzhash anywhere — and `defaultSplitterFactory` has never been assigned anything else; the `rollingHashSplitter` that imported kch42's coordinate was reachable from exactly one place, its own benchmark, and rode into the binary only because Go links at package granularity. The silvasur coordinate sat even further out, in `store/nbs/benchmarks` — a hand-run benchmark harness nothing in the module imports. The dolt fork now deletes both (patch 3 in `FORKS.md`): the dead splitter, its benchmark, and the benchmarks tree, producing no new code, copying nothing, and shipping no WTFPL text to anyone. This is the epic's worked example of "cut" beating both "copy" (kch42's authored table constants in a file we claim copyright over) and "rewrite" (our own maintenance burden for a component nothing calls). That the deletion moves no chunk boundary was measured, not argued — twice, against the pins on both sides; the evidence lives with the patch, in `FORKS.md` patch 3. `policy.json`'s buzhash exception is deleted (fslock's is now the only one left), `LICENSE-REPORT.md` carries no Unknown row, and the linked component count drops from 155 to 154.
- `lit` now builds Dolt and go-mysql-server from forks owned by the `promptctl` organization. `go.mod` previously replaced `github.com/dolthub/dolt/go` with `github.com/brandon-fryslie/dolt/go` — a personal account that `promptctl-deps-4aes` already names as a single point of failure for master's build, and that an auditor reading `go.mod` under the zero-copyleft bar asks about out loud — and it did not fork go-mysql-server at all, even though one file in that module (`sql/cache.go`) is the sole reason an MPL-2.0 dependency is linked into the binary. Both now resolve to `promptctl/dolt` and `promptctl/go-mysql-server`, each on a branch named `lit` based on exactly the upstream commit `go.mod`'s `require` line still names, so `git diff <require-commit>..lit` answers "what did lit change?" as a command rather than as a claim some document makes. The forks are permanent even though the one patch they carried when created (dolt's git-blobstore ranged-read materialization, upstream PR dolthub/dolt#11264) is not — removing a transitively imported copyleft module means changing what the importer imports, and that needs a fork to change it in. Forking Apache-2.0 code brings obligations `lit` did not previously owe, so every file the forks modify now carries a section 4(b) change notice under its upstream copyright header, upstream `LICENSE` files are byte-unmodified, and both upstreams were checked for a `NOTICE` file — neither ships one, so there is nothing to propagate. The new root-level `FORKS.md` is the contract: the patch ledger with a retirement condition per patch, the rebase procedure, and `go run ./tools/licenses -check` as the check that a rebase did not quietly restore a copyleft import. The `go.mod` comment that used to summarize the dolt patch now points at that ledger instead of restating it, having already drifted into calling a now-permanent fork "transient."
- A reconcile that folds one side's work onto the remote spine — the shared-history field-aware reconcile, the unrelated-history `lit sync reconcile combine`, and `lit sync reconcile take local` — now preserves the folded side's per-commit provenance instead of flattening it into one squash commit. Each local commit the spine lacked lands as its own forward commit with the original message, timestamp (second precision), and author, projected as its merge with the remote content so every mid-chain state is a whole backlog; commits whose projection changes nothing (for example schema/migration-only commits whose work the lift commit already carries) are dropped rather than replayed empty. A marker commit naming the operation still settles the sequence — its diff is exactly what the merge policy itself decided beyond the folded side's content (the agent's prose resolutions on a finalize; for take-local, the owner-approved discard of the remote-only issues), and when the remote head is at an older schema one machinery commit (`reconcile: lift remote head to current schema`) precedes the provenance commits with the schema DDL and its bookkeeping. The final backlog contents, linear history, and fast-forward push are unchanged from the squash behavior. The reconcile result and the command output now report how many commits were replayed. In the 2026-08-08 field incident one machine's entire pre-reconcile history flattened into a single merge commit — the data survived but what changed, when, and in what order did not; that record now survives the fold, at exactly the moment someone reconstructing a divergence needs it.
- A burst of mutating commands now coalesces its on-change push mirrors through a `mirror-pending` marker in the workspace's storage dir, instead of one fork/exec per mutation — most of which existed only to lose the single-flight race while adding real process-table and CPU pressure on a loaded machine. A mutation that finds the marker provably still answered for rides along (the covering push has provably not started, so its HEAD read will include the mutation); otherwise the mutation claims the marker and spawns the mirror itself, and every push attempt clears the marker as it starts (as first landed, "still coming" was read from the marker's freshness under a five-minute age bound; the mirror-beacon entry below replaced that reading with a kernel liveness proof within this same release). A burst therefore runs a handful of mirrors — roughly one per completed push — rather than one per mutation or even one per second, and coalescing loses nothing: each mirror pushes the current HEAD, which includes every commit that landed before its engine opened.
- The default `sync.cadence` is now `on-change` instead of `on-push`: a mutating command (`new`, `start`, `update`, `close`, `comment`, `rank`, …) on a connected workspace now mirrors to the remote in the background without a separate `git push` or `lit sync push` step. Previously eager push was opt-in config a workspace had to know to set; the links-sync-pgct field incident happened specifically because push stayed a manual act nobody remembered to do, stranding 25 local changes for days with nothing surfacing the drift. The mirror itself and the `on-push`/`on-change` policy machinery both predate this change (#226, #227) — this flips which value a workspace falls into with no config file at all. `on-push` (mirror only via the pre-push hook) remains available for a workspace that deliberately wants to batch outgoing pushes; set `[sync] cadence = "on-push"` to opt back in. A push that stays pending for any reason — cadence set to `on-push`, the background mirror failing, or an unreachable remote — is not silent either way: `lit backlog`/`next`/`show` print the "N local change(s) not pushed" line, and (since the push-outcome marker landed, above) a failed attempt also surfaces as a `FAILING` banner on every mutating command, not just those three reads.

### Fixed

- The `lit snapshots new` copy can no longer capture a journal torn by a concurrent command's crash recovery, and lit's engine lock — the shadow that left that window open — is retired. The window was measured, not inferred: embedded Dolt's read-only mode is not a caller choice but the contention fallback on its own `.dolt/noms/LOCK` (a 100ms flock attempt at engine open), lit never requests a read-only open, and so a plain `lit backlog` on an idle store opens write-capable and runs journal crash recovery — with a dirty journal and the LOCK free, a *read command* truncated the journal 98473 → 98457 bytes and fsynced it; with the LOCK held, the same command served the same reads and wrote nothing. lit's `.links-engine.lock` was a partial second representation of that same fact, taken by `Open`/`OpenSync` but not by `OpenForRead`, which is exactly why the copy could not close the window by taking it: it would have excluded writers and zero readers. Now the copy holds Dolt's own LOCK (via the same `internal/filelock` primitive — Dolt's fslock is plain flock) for the whole walk, after the workspace hold and before the commit lock per the declared order; under the hold a concurrent read open demotes to the write-nothing read-only fallback while a write-capable open refuses the fallback and fails fast after its bounded ~30s retry — either arm writes nothing. A regression test replays the measured experiment on both arms (dirty journal unchanged under the hold; the same journal truncated by the same open once released). The engine lock is deleted rather than kept as a third name for one condition — the bounded ~30s wait it provided at write-open collisions (links-sync-pgct.11) is already provided by the write-open retry against Dolt's LOCK, and write engines now open eagerly at store construction (before any commit lock) rather than lazily at first SQL — read engines stay lazy, since they never wait on LOCK and a lazily-opened reader can still come up write-capable for auto-migration once a transient holder clears — shrinking the documented LOCK-under-commit order deviation to the one unavoidable site, the mid-mutation GC reconnect. A journal-lock holder that outlasts the retry now surfaces with holder-naming guidance instead of a raw "database is locked". Residuals, stated rather than implied: `journal.idx` has no can-write gate (opened O_RDWR, truncated on every bootstrap), so a copy can still capture a torn index — a severity downgrade, not a hole, because a torn index self-heals on the restored store's first open (`corruptIndexRecovery` rebuilds it from the journal) where a torn journal would be data loss. And a read command whose workspace has PENDING schema migrations now fails loudly during a concurrent snapshot copy — its lazy engine resolves under the held lock into the permanent read-only fallback and the migration DDL cannot apply, so `OpenForRead` returns retry-after-holder guidance instead of the raw read-only line; reads at current schema serve normally from the fallback. That loud, retryable failure is the deliberate trade against the pre-PR behavior, where the same interleaving silently risked the torn snapshot this entry closes.
- `Store.ClearParent` and `Store.RemoveLabel` no longer discard the error from `RowsAffected()` after their `DELETE`; a genuine driver/query error reading the affected-row count now surfaces as that error instead of being misread as a false "not found" (matching the pattern already used by `RemoveRelation` and the issue-status/retention writes).
- `Store.RemoveLabel`'s zero-rows case now returns `NotFoundError` instead of a plain error, matching every other not-found path in the store; a `lit label remove` of a label that isn't on the issue now exits with the correct not-found exit code instead of falling through to the generic one.
- `internal/cli/sync_failure.go`'s doc comment on `syncFailureUnrelatedHistories` no longer claims the wholesale/union resolution surface "is not yet built" — `lit sync reconcile combine` and `lit sync reconcile take <local|remote>` already exist and are what the class's rendered guidance names (the comment had drifted from `resolutionSteps()`, which already listed all three commands).
- `lit init`'s remote-adopt step no longer treats a detection/clone failure (reading the local store, resolving the remote, `git ls-remote`-style ref/data checks, or the clone itself erroring) the same as a confirmed-empty remote. Previously it warned and proceeded to create a fresh local store regardless, which risked silently stranding a real remote backlog behind a transient credentials/network/URL problem. Now `lit init` exits non-zero, creates no store, and surfaces the real underlying failure (with the dev-vs-release build status named alongside it) instead of a generic "could not pull existing backlog" warning; retrying `lit init` after the cause is fixed behaves exactly as before. The three genuinely certain-empty outcomes (no remote configured, a remote with no refs, a remote with refs but no lit data) are unchanged — automatic, silent, no gate.
- A mutating command run right after another on a connected workspace could hit `Error 1105: cannot update manifest: database is read only` instead of completing — pre-existing exposure from #226/#227 that links-sync-pgct.3's on-change-by-default flip made everyone's default instead of an opt-in a power user chose knowing the tradeoff. The root cause was two embedded-Dolt behaviors stacking: an engine open that finds the exclusive journal-manifest lock held by another process (an earlier command's still-exiting push mirror, say) silently opens READ-ONLY instead of failing, and dolt's in-process singleton cache then pins that read-only store — journal lock included — until process exit, so no amount of in-place retrying or connection rotation could ever recover; the command was doomed at open time and only found out at commit time. Now every store open bypasses the singleton cache (a `Store.Close` really closes its engine and releases its journal lock, instead of a cached shadow outliving it), and write-capable opens (`Store.Open`, `Store.OpenSync`, the bootstrap and adopt-clone opens) additionally fail fast on a foreign journal-lock holder and retry the open itself — bounded ~30s, honoring command cancellation — until the holder clears, so a successfully opened write store is structural proof it can write. `Store.OpenForRead` keeps dolt's read-only fallback: reading beside a live writer is exactly a read open's contract. That bounded open retry against Dolt's own journal lock is the serializer among lit's processes — as first landed, a lit-minted engine-write flock sat in front of it as an outer serializer, but the engine-lock retirement (above, this same release) removed that shadow once the retry alone was shown to carry the whole contract. A scripted burst of back-to-back mutating commands against a connected workspace no longer produces this error on any of them.
- `withMutation` no longer re-runs a mutation's body when only the final Dolt versioning step (`DOLT_COMMIT`) failed transiently: the retried unit now resumes at the first phase that hasn't succeeded, so once the staging transaction has committed the retry repeats only the versioning step. Previously the whole-unit retry re-applied the body against its own already-staged writes, which could double-apply a mutation (for `lit new`, a duplicate issue minted under a higher collision nonce) in the narrow window where the SQL commit landed but the versioning commit hit contention.
- The last mutation of a burst can no longer strand its push until the next activity. Under the interim one-spawn-per-second debounce, a mutation landing inside the window spawned no mirror and bet on an earlier, still-live mirror reading HEAD after its commit — but that mirror holds the workspace's one write engine while it pushes, so any mutation it blocked committed strictly after its HEAD read, and the burst's final mutation (exactly the moment an agent walks away) was a coin toss between "pushed now" and "sits local until the next mutation, a 24h staleness banner, or an explicit push". Coverage is now owned state with no time constant carrying it: a mutation either observes a `mirror-pending` claim whose mirror provably hasn't read HEAD yet, or claims it and spawns the mirror itself; a mirror that finds the marker re-claimed after its push runs another full cycle on a fresh engine before exiting, so custody of the tail passes mirror-to-mirror instead of resting on timing (as first landed, the marker's age carried crash recovery — a five-minute bound re-claimed a marker whose mirror died before pushing; the mirror-beacon entry below replaced that last timing guess with a kernel liveness proof within this same release). Mirror failures *before* the push attempt — the spawning command never exiting, the engine failing to open, the mirror failing to spawn at all — previously wrote no `push-outcome.last` record and sent no owner notification (only a trace); they now complete through the same push-outcome record as an attempt that ran, so the mutating-command `FAILING` banner and the `sync.owner_notify_cmd` channel report a push layer that cannot even start exactly like one whose pushes fail. Two endings that are not channel degradation get their own non-failed record classes instead of `error`: a deliberate cancellation (ctrl-C, process teardown — previously left the FAILING banner coloring every later command) and a mirror timing out behind another lit process legitimately holding the workspace's one write engine (a long reconcile or import — previously would have paged the owner over healthy local serialization); a mirror dismantled mid-startup by SIGTERM releases its claim and records nothing, leaving the last completed attempt's record standing. A panic mid-push now records itself as the attempt's ending instead of unwinding into a fabricated healthy "pushed" record. Remote-less workspaces re-confirm their absence at most once per 10s (`remote-absent.last`) instead of paying a git subprocess per mutation. The burst regression test now proves delivery of all its commits by oracle poll alone, with no explicit sweep push.
- A `lit init` backlog adopt interrupted mid-clone can no longer leave a partial database that later commands treat as the real store. Adopt now writes a durable adopt-pending marker (temp-file-and-rename plus fsync, so a torn or lost marker is unrepresentable) inside the Dolt root before its destructive window opens, and clears it only after the clone's product is validated — so the failure shapes that can run no in-process cleanup (init's 120s deadline abandoning the clone goroutine and exiting, SIGKILL, power loss) leave the marker as durable proof the directory holds an adopt's leftovers, not a backlog. Every normal store entry point (`Open`, `OpenForRead`, `OpenSync`, `EnsureDatabase`, `DumpRaw`) refuses a marker-present workspace loudly, naming the interrupted adopt and the remedy — most critically `lit new`, whose `CREATE DATABASE IF NOT EXISTS` bootstrap would otherwise bless the residue as a fresh store and re-create the links-sync-pgct field incident (a fresh workspace silently shadowing the remote backlog). The check runs after each entry point's workspace lock is held, never before, so a live adopt (which holds the lock exclusively) reads as ordinary workspace-busy while a marker seen under an acquirable lock always means a dead one — no false "interrupted" verdicts during a healthy adopt, and no stale pre-lock answer sailing into residue after an adopt dies mid-wait; standalone `EnsureDatabase` now takes the same workspace lock as `Store.Open` for its bootstrap, closing a pre-existing window where an unlocked `CREATE` could race an adopt's destructive window (as first landed it also took the since-retired engine lock; its write-engine opens serialize on Dolt's own journal lock, per the retirement entry above). A plain `lit init` retry heals with no manual cleanup: init's adopt gate reads the marker as "nothing to lose" (the marker is only ever written after that same gate confirmed the store held no tickets), sets the leftover ASIDE as a sibling `dolt.adopt-displaced-<ts>` directory — displacement, never deletion, so even tickets minted over residue by a stale pre-marker binary stay recoverable — re-clones, and clears the marker; when the workspace holds residue but the remote signal is gone (removed remote, no refs, no lit data), init refuses with the one interrupted-adopt verdict instead of narrating "starting with an empty backlog" and then failing. A clone failure that returns normally still leaves a fully clean slate — no partial database, no marker — with lit removing its own partial clone unconditionally rather than relying on dolt's best-effort courtesy cleanup, and the marker deliberately lives inside the Dolt root (unlike the sibling lock files) so `lit snapshots restore`'s wholesale directory swap clears or preserves it in lockstep with the data it describes.
- `lit snapshots new` can no longer copy the Dolt directory while a directory-rotating operation is rewriting it. The snapshot copy ran under only the store commit lock, while the destructive windows of `lit snapshots restore`, a remote adopt (displace + `DOLT_CLONE`), and a workspace promotion run under the workspace-exclusivity lock — two disjoint lock files that never contend — so a snapshot started during an adopt walked and copied files the clone was concurrently creating: at best a spurious mid-walk failure, at worst a torn snapshot sitting in the listing as a restorable recovery point that is actually a corrupt store. The copy now takes the same shared workspace hold every store open takes (new `store.LockWorkspaceShared`), acquired before the commit lock in the same workspace→commit order the rotators and store opens already use: it contends with every rotator's exclusive hold — refusing workspace-busy after the same ~5s grace every reader extends a transient rotation, creating no artifacts — while coexisting with concurrent ordinary readers, which hold shared too. The shared-acquisition busy message also stops naming `lit snapshots restore` as the only possible exclusive holder — adopt, promotion, and lifeboat recover's heal take the same lock, and mislabeling the culprit sent the operator looking for a restore nobody ran. Two adjacent gaps in the same command closed in review: `lit snapshots new` now honors the adopt-pending condemnation the way every store open does (checked under the held workspace lock), refusing to snapshot a dead adopt's partial residue as a "restorable" recovery point — previously the copy would install the garbage in the listing and the retention prune could then evict a good snapshot to keep it — and a stray positional argument (`lit snapshots new nightly` — natural, since sibling `restore` takes its argument positionally) is now a usage error instead of silently minting an unlabeled snapshot the operator can't find by the name they thought they gave it. The retention prune also runs after the workspace hold is released — it never reads the Dolt directory, and a multi-gigabyte snapshot deletion should not keep a rotator refusing workspace-busy.
- An interrupted snapshot copy can no longer permanently orphan invisible full-size residue. `dbsnapshot.Take` was context-blind and the CLI interrupt guard hard-exits after its grace period, skipping Take's only cleanup sites — so a Ctrl-C/SIGTERM mid-copy (easiest to hit on filesystems without reflink, where the copy is a real multi-second byte copy) stranded `snapshots/<ts>.tmp` (up to store-size) plus `<ts>.reserve` on disk forever: `lit snapshots list` and every retention prune filter those names, so the residue was invisible to every lit command, untouchable by retention, and each repeated interrupt ate another store-sized chunk. Two halves close it. The copy is now context-aware — cancellation is honored between files and between 32MiB chunks of one large file, so an interrupt aborts the walk and runs Take's own cleanup (the partial `.tmp` and the `.reserve` claim both come off disk) inside the interrupt guard's grace instead of the process dying tree-half-written. And the failure shapes that can run no cleanup at all (SIGKILL, a hard exit mid-cleanup, power loss) are reclaimed at the next take's entry — the one point every snapshot producer (user snapshots, migration/downgrade/reconcile recovery points) reaches on every attempt *before* new disk is consumed, so in the disk-full regime the retry reclaims the dead predecessor's store-sized corpse first and then succeeds (wiring collection downstream of a successful take, e.g. into the retention prune, is unreachable in exactly that regime). Collection is safe under a new producer beacon — an flock inside the snapshots directory that every `Take` holds shared for its whole reserve→copy→rename window, so acquiring it exclusively is kernel proof (no age thresholds, no PID files; a dead holder's lock evaporates with its process) that every producer artifact present belongs to a dead producer. When the probe finds a producer alive, collection simply defers to a later take — reclamation is delayed, never forfeited. One caveat qualifies the proof during a mixed-version window: a still-running pre-beacon binary's live Take holds no beacon, so it reads as dead and its in-flight artifacts are collectible; the exposure needs an old binary running beside a new one and retires with the old binary. Destruction is deliberately narrower than rejection: only names whose full shape lit provably minted (a parseable `<unix-ns>[-label]` head under `.tmp`/`.reserve`, or the collector's own `<artifact>.<ns>.condemned` — the bare suffix is never provenance, so a foreign `backup.condemned` is as untouchable as a foreign `backup.tmp`) are collectible, staying as inert to the collector as to every other consumer. Snapshot labels are also capped (128 bytes, at the one lossy normalizer that already rewrites them) so the condemnation rename always fits NAME_MAX — an uncapped near-limit label could previously strand a killed take's corpse behind ENAMETOOLONG forever. The collector's exclusive window covers only classification (renaming dead artifacts to fresh `.condemned` names, sub-millisecond); the multi-gigabyte deletions run after it releases, and a collection failure of any kind is loud on stderr but never fails the take (or the migration/downgrade carrying it) — the same post-durable-success demotion the reconcile prune already uses. Closed alongside, from the same missing predicate: `lit snapshots restore` of a labeled crash-leftover (`<ns>-<label>.tmp`, whose digit head parses as a valid timestamp) was accepted by restore's name validation even though the listing would never show it — restoring one would install a torn partial copy as the database; producer-artifact names are now rejected inside the one name predicate the listing, validation, and the collector all share. Two adjacent gaps in the same copy path closed in review: the destination file's close error is now part of each file copy's outcome instead of being discarded by a defer — on write-back-at-close filesystems (NFS commit-on-close, delayed-allocation ENOSPC) that dropped error was the only signal the file is truncated, and swallowing it let a torn copy rename into the listing as a restorable snapshot. The flock primitive itself (POSIX flock(2) / Win32 LockFileEx, previously private to the store's workspace/engine/sync-push locks) moved to a shared `internal/filelock` package that reports contention as a value rather than an error, so the store's locks and the snapshot beacon ride one platform seam instead of two.
- The commit lock can no longer evict a live holder. It was the one lock still built on an `O_CREATE|O_EXCL` file carrying its owner's PID, judged stale by a ten-minute mtime threshold OR a signal-0 liveness probe — the OR meant age won alone, and it was measured doing so: with a live process holding the lock and the file backdated eleven minutes, a mutation from a second process walked straight past the owner and exited 0. `takeUserSnapshot` holds this lock for its entire copy, so any snapshot running past ten minutes admitted a concurrent writer into its own walk. Release compounded it: the closure deleted the lock path unconditionally, with no way to tell "my lock" from "a lock", so after one eviction the first finisher deleted the second's lock and a third acquired cleanly. The lock is now an flock through the same `internal/filelock` boundary every other lit lock uses — the hold lives on the holder's open file description, so the kernel releases it on any death mode with no threshold to tune, releasing yours cannot touch anyone else's, and a leftover lock file from a crash (or an old binary) is just residue that never blocks. The PID write/read, the signal-0 probe, the mtime staleness classifier, the delete-on-release, and the process-level acquisition mutex (flock already excludes between goroutines — separate opens get separate file descriptions) are all deleted rather than replaced. The lock also gains what it alone lacked: a declared ~15-minute retry budget (sized to the lock's longest legitimate holder — a snapshot copy of a large store without reflink, measured past the old ten-minute threshold — so a healthy long copy keeps concurrent writers waiting exactly as the old unbounded loop did, while a genuinely wedged holder finally surfaces as a clear error instead of queueing callers forever; context cancellation escapes the wait at any moment) and contention that surfaces as the store-wide `ErrWorkspaceBusy` sentinel with commit-specific operator guidance, instead of an untyped `lock not acquired` string no caller could discriminate. Nested acquisition by the same mutation still short-circuits via the same context marker as before. The flock lives at a fresh path, `.links-commit-flock.lock`, because the historical name is burned: an old binary's release (and its ten-minute age eviction) `os.Remove`s `.links-commit.lock` unconditionally, and an unlink under a live flock splits the lock across two inodes — the next acquirer opens a fresh inode and runs concurrently with the orphaned holder, a corruption that would outlast the old binary's exit. A name no historical binary ever touches makes that split unrepresentable. One honest caveat remains: an old binary's `O_EXCL` lock and the new flock do not exclude each other at all, so mixed-version writer exclusion holds only once the old binary exits — the same retiring exposure the snapshot-residue collector already documents. Closed in review alongside: `filelock.Acquire` only observed its context in the sleeps between attempts, so a cancellation landing at the final attempt (or on a single-attempt probe) reported clean contention — dressing an operator's Ctrl-C in "another holder is busy, retry" guidance — and an already-cancelled context still acquired (and then held) a free lock, letting a SIGTERM'd command admit its guarded operation into the interrupt grace; `Acquire` now refuses a done context at entry and surfaces `ctx.Err()` over clean contention, for every flock in lit. And a commit-lock release failure after the guarded operation already succeeded no longer converts that durable success into a reported failure (the hold is provably gone — closing the descriptor releases an flock — and a failure exit invites retrying a mutation that already landed into a duplicate): it is loud on stderr and the command reports its success, joining the operation's error only when the operation itself also failed.
- Whether an on-change mirror is still alive is no longer guessed from a five-minute age bound on the `mirror-pending` marker — the last wall-clock liveness inference in the tree. The bound was crash recovery for SIGKILL-class deaths (every ending that runs code removes or completes the marker itself), sized by summing worst-case healthy delays — the mirror's parent-exit wait, an engine-open budget, a full predecessor push cycle — exactly the kind of estimate a loaded machine outgrows first: a healthy-but-slow mirror past the bound drew a redundant re-claim, while a SIGKILLed mirror's residue falsely covered every mutation for up to five minutes. Liveness is now the kernel's answer, on the pattern the snapshot producer beacon already demonstrates: every answerer for the marker holds a shared flock (`.links-sync-mirror.lock`, a sibling of the Dolt directory like the sync-push lock) — the claiming command from its claim (the hold is minted inside the claim itself) until its obligation ends: released together with a claim it un-claims, kept to process exit once its mirror is spawned — pinned in a package-level GC root, because Go's `os.File` finalizer would otherwise close the descriptor and drop the flock at the first garbage collection after the claiming function returns, ending the hold silently mid-process; and that mirror from its own entry (before its parent-exit wait), overlapping lifetimes, so coverage has no window in which a healthy spawn reads as dead — until any death mode releases it. A claim that finds the marker present parses the beacon with a two-step probe, shared first, exclusive as the deciding last step (single attempts, each released the instant it succeeds): a failed final exclusive attempt proves someone — whose every code-running failure path clears the marker loudly — held at that instant, and the marker is covered; a successful one is kernel proof every answerer is gone, including one that died between the steps, and the marker is residue to re-claim on the spot; and an exclusive holder at the shared step — a foreign squatter, or the instant of another claimant's own probe — is never read as covered: the claim spawns, and the spawned mirror either takes the beacon normally or fails its own hold loudly against the persistent squatter. No threshold to tune, no clock consulted — the age-out's dedicated backward-clock-step branch deleted with it. The marker itself stays a plain file owning only "is a mirror still owed" (its mtime still the claim stamp the single-flight holder's post-release re-check orders by); the beacon is deliberately a second file rather than an flock on the marker, because push attempts remove the marker — and historical binaries always will — and an unlink under a live flock splits the lock across two inodes, the same lesson that moved the commit lock to a fresh name. The beacon proves owner liveness, precisely the discriminator the age bound was guessing at; it does not and cannot prove a future push lands — pre-push deaths that run code still record through the shared push-outcome seam, and a mirror that cannot take the beacon (nothing legitimate holds it exclusively past a probe's instant) refuses to run through that same seam, recorded as a FAILED ending that raises the FAILING banner and pages the owner — a stopped push channel is degradation, never the non-paging workspace-busy class, which stays reserved for healthy engine serialization. The claim protocol's documented double-spawn tolerance is preserved rather than traded for a new failure mode: racing claimants may still both spawn — now confined to probe-instant windows, since the claimant's own hold spans the whole spawn window — serialized by the single-flight lock into one push and one cheap no-op, and a still-running pre-beacon binary's mirror reads as dead for the same bounded cost, an exposure that retires with the old binary. One deferral survives every scheme and is stated rather than implied: a claim can read covered off an answerer — a racing claimant, or a mirror mid-exit — that then fails before pushing; every such failure that runs code records the FAILED outcome, the banner, and the owner page, and the push waits for the next occasion — deferred loudly, never stranded silently, with SIGKILL-class deaths of the last answerer leaving residue the very next claim's unheld verdict recovers. With this the lock discipline's declaration holds with no straggler: every liveness question on a workspace's Dolt directory is answered by exclusive acquisition, and `internal/filelock`'s doc names no mechanism predating the rule.
- `lit snapshots new` and `lit snapshots restore` print their result record the moment it is durable — before retention pruning, and beside any failure that lands after the take or the rotation — so a post-success failure can no longer hide that a snapshot now sits in the listing (baiting a duplicate retake) or that a restore already consumed its snapshot and set the previous directory aside (baiting a retry that reports the snapshot missing). A restore that fails between its two renames — the previous directory already moved aside, the snapshot not yet installed — names the rotated-aside path in its error, so the operator's only pointer to their displaced data is never swallowed by the failure that displaced it.
- `lit snapshots new`'s user-retention prune no longer counts reconcile recovery snapshots against the user budget. `pre-reconcile` rollback points share the `snapshots/` directory, and once the user budget was exceeded the oldest of the combined set rolled off — silently evicting a recovery point the reconcile system's own independent budget was supposed to protect, exactly as the kind filter already spared migration and downgrade snapshots. The user-kind predicate now excludes all three system producers.

### Fixed

- Sync reconciliation of branches with unrelated histories no longer depends on a silent error-swallowing bug in the embedded Dolt driver. The driver's first-row pre-read discarded any error, so a query that failed on its first row (such as `DOLT_MERGE_BASE` raising "no common ancestor" for refs that share no history) could surface as an empty result set instead of the real error. The driver now propagates that error, and merge-base resolution recognizes the "no common ancestor" backend error as the unrelated-histories state directly — the same domain outcome it already handled via an empty result set.

### Removed

- Three single-purpose commands are folded into flags on broader commands and retired as standalone verbs, each with a documented pointer (no capability lost): `lit assign <id> <name>` → `lit update <id> --assignee <name>` (reassigning is a single-field write; `update` already owns field mutation, including the optional `--reason`); `lit ls-at <dir>` → `lit ls --at <dir>`; `lit overview` → `lit stores --counts`. The retired verbs stay dispatchable but hidden, so an old invocation returns a pointer to the surviving flag (exit 3) instead of cobra's bare unknown-command error — the break is deliberate and named, never silent.
- `lit bulk import` is retired: it was a second name for the export-restore that `lit backup restore --path <export.json>` already owns (both ran the identical restore path), and it was the odd verb out in a family of per-`--ids` fan-out operations. An old `lit bulk import` invocation now returns a documented pointer to `lit backup restore`. `lit import` remains the one home for JSON tree-spec imports — a distinct operation that only shared the word "import."
- `lit update --status` is retired: `update` no longer changes an issue's status. The transition verbs (`lit start` / `lit done` / `lit close` / `lit open`) are now the single enforcer of the transition guardrails, so `update --status` is rejected with a documented pointer to them instead of routing status through a second, divergent path. This closes the former `--status closed` back door, which recorded a resolution-less `done` and bypassed `close`'s required outcome. The capability is fully reachable under the verbs; the break is deliberate and named, never silent. `update` remains the home for field edits (`--title`, `--description`, `--assignee`, `--labels`, `--lane`, etc.).
- The `ready` and `queue` workable views are retired from the command surface, leaving `next` (the single leaf to start) and `backlog` (the full ranked queue with blocked items shown inline) as the only named workable views — `ls` remains the power query and `orphaned` its own staleness view. `lit ready` and `lit queue` no longer appear in `lit --help` or shell completion, and now fail with a documented pointer to `lit backlog` / `lit next` instead of running: the break is deliberate and explained, never silent. The retired presentations (ready's blocked-to-bottom re-sort and coaching preamble; queue's terse pullable-only list) are dropped — `backlog` and `next` carry the surviving intent.

## [0.2.1] - 2026-08-01

### Changed

- Rewrote lit's agent-facing prompt surfaces (the CLAUDE.md integration block `lit init` writes, and the `lit quickstart` guidance) into calm, plain, second-person tool documentation. The agent-native workflow is unchanged; only the register is.

## [0.2.0] - 2026-07-30

### Added

- In-repo issue tracking backed by an embedded [Dolt](https://www.dolthub.com/) database — the backlog ships with the code and every mutation is a versioned commit.
- Agent-first core loop: `lit ready`, `lit start`, `lit done`, and `lit followup` return guidance alongside data so a coding agent can drive the workflow unattended.
- `lit quickstart` prints the live command reference for agents.
- One write boundary and one identity per clone, keyed off `git rev-parse --git-common-dir`, so all worktrees of a clone share a single issue view.
- `lit version` command with build-time `-ldflags` version stamping.
- `lit doctor [--fix]` for diagnosing and repairing workspace issues.
- `lit lifeboat` recovery path for schema-ahead workspaces.
- `scripts/install.sh` builds `lit` from source and installs it onto `PATH`, warning about stale shadowing binaries.

### Changed

- `lit new` and `lit followup` now rank new tickets to the **top** of the order by default (fresh work surfaces first) instead of the bottom. Pass `--bottom` to append at the bottom — use it when authoring a batch in order so creation order is preserved. Importing an existing backlog still preserves its order.

### Fixed

### Removed

- The `--json` flag is removed from every command. The default human-readable text is the one canonical surface — it is already the agent interface, and per-line output is parseable when a script needs one field (e.g. `lit workspace | sed -n 's/^traces_dir: //p'`). `lit export` and `lit lifeboat dump` are unchanged: they emit a JSON data structure as their sole output (no flag), because a full export / raw dump has no text form. Passing `--json` now fails with a usage error.
